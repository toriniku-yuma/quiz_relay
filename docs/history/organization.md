<summary>今回の実装</summary>

- 組織、共通アカウント、インスタンス、担当権限の4表。singleton制約で1配置1組織。初回設定は指定Auth subjectとサーバー検証済み本人を照合し、組織・管理者・最初のインスタンスを同一TXで作る。

  初回設定の競合はadvisory lockと制約で防ぐ。
- 組織のidentityNamespaceは旧GAME_OWNERを保持。既存と同じハッシュでactorIdを求め、表示名・メール・選択インスタンスを本人統合に使わない。組織名とアカウント権限を本人IDに混ぜない。
- 最初のインスタンスのownerは旧GAME_OWNER。追加先はUUIDに対応する `urn:uuid:<UUID>` を内部データキーとする。既存HTTPS ownerも有効。

  URNは通信先ではなく、連合の外向け識別・署名設定は第5段階で別途設計する。
- 専用DBロールquiz_organization。既存reader・結果writer・CLI管理ロールから分離し、組織表の必要な操作だけを許可。識別子列の更新権限を与えず、管理接続による誤更新も不変トリガーで拒否する。
- 初回設定、インスタンス一覧・追加・名称変更・公開開始、共通アカウント確認、インスタンス別担当権限の画面とAPI。追加は準備中。一般一覧に出さず、通常対戦・履歴APIへの直接アクセスも拒否。公開取消は追加していない。
- `?instance=<内部UUID>` を対戦・取消・復帰・履歴・WebSocketで明示する。ownerとactorはWorkerで解決し、本文の指定値を信用しない。

  部屋の保存済みinstanceIdとWebSocketの対象が異なれば拒否。タブの復帰情報も本人・インスタンス別。
- 組織ID名のMatchmakerでactor予約を共通化し、待機列はinstanceIdと固定版で分離。部屋数上限はインスタンス別。

  リクエスト回数制限は組織共通actor別で、既存maxRateActorsは組織の防御上限として扱う。規模・負荷の実測は未実施。
- DB・部屋RPC待ちを組織のストレージ直列区間から分離。参加前に部屋・世代を保存し、取消は部屋側に世代を閉じてから同じ予約を解放する。部屋未作成時の取消も永続化し、遅延予約を拒否。RPC結果が不明なら予約を保持する。

  ログアウトはトークンを失効させ、進行中の参加枠を保持する。
- 終端の参加枠解除と結果保存の再試行を分離。結果writerへ渡すownerは保存済み部屋の値。原本・outbox・既存固定版を書き換えない。
- 現行の固定セットで利用可能な候補が0件ならNO_RANKED_QUESTIONS。新規参加を拒否し、組織MatchmakerのAlarmでも検出して待機だけを解除する。開始済み試合は固定問題で継続。

  復旧後は新しい参加要求で再評価し、自動で待機へ戻さない。現行セットの一部だけが停止された場合の既存エラーは維持し、第2段階のカテゴリ自動選出が完成したことにはしない。手動休止機能自体は第3段階。

### R01 / P1 / ログアウトと復帰の競合で同時参加制限が破れる【再現済み】

箇所：[Matchmaker.reserve](../../src/worker/matchmaking/Matchmaker.ts) 138–166行、cancel 188–200行、[GameRoom](../../src/worker/game/GameRoom.ts) 60–64行・177行。

ログアウトは部屋側で旧tokenを失効させ、そのRPCから戻った後でMatchmakerのtokenを交換する。その間の復帰要求は旧tokenでreserveを呼び、STALE_RESERVATIONになる。

reserveはこの失敗だけで組織の参加枠を削除する。GameRoom側には進行中の参加者が残るため、同じアカウントが別インスタンスへ新規参加できる。

再現手順：Aの2人対戦をREVEALINGにする → aのlogoutを開始し、部屋側の失効成功後のRPC応答だけを保留 → aがAにresumeするとSTALE_RESERVATION → aがBへjoinすると成功。

元の部屋はREVEALINGでaを保持していた。

修正の方向：失効処理中の世代・token遷移を組織側に保存し、再開要求と整合させる。reserve失敗を一律に「進行中の参加がなくなった証明」と扱わない。RPC途中で再起動する場合も含めて試験する。

### R02 / P1 / 組織画面や別インスタンスからのログアウトがゲーム権限を失効させない【コード確認】

箇所：[OrganizationGateway](../../src/client/features/organization/OrganizationGateway.tsx) 32行、[useMatchmaking](../../src/client/features/matchmaking/useMatchmaking.ts) 89–92行、[matchmaking routes](../../src/worker/matchmaking/routes.ts) 22–23行。

組織一覧のログアウトはauth.logoutを直接呼ぶ。別インスタンスBを閲覧していてBのgame.roomIdがない場合も、参加中のAに対する失効要求を送らない。

WebSocket経路はSupabase認証より前に登録され、部屋Cookieだけで認可するため、AuthからログアウトしてもAのCookieと部屋セッションは有効なまま。同じブラウザーから旧参加者として接続できる余地が残る。

CookieはHttpOnlyでも、ブラウザーによるWebSocket送信は可能である。

修正の方向：閲覧先ではなく組織共通の参加情報から失効対象を解決し、すべてのログアウト入口を統一する。ログアウト時に進行中の参加枠を保持する仕様は維持する。アカウント切替、別タブ、復帰情報がないタブでも試験する。

### R03 / P1 / 通常アクセスが回収アラームを延期し続け、終了済み部屋で満員になる【再現済み】

箇所：[Matchmaker](../../src/worker/matchmaking/Matchmaker.ts) 33行、112–120行、261–265行。

enter時に回収するのは要求者自身だけ。一方、queueへのすべてのwriteがアラームを「現在時刻＋60秒」に再設定する。60秒未満の間隔で要求が続くと全体回収が実行されず、他の利用者の終了済み・期限切れ予約が残る。

maxRoomsは保存された予約のroom数を数えるので、実際は終了済みでも満員になる。RATE_LIMIT等の失敗経路にもアラームを延期するwriteがある。候補0件検知の定期処理も同じアラームに依存する。

再現手順：同じインスタンスに終了済み64室の予約を保存し、1秒後の回収アラームを設定 → 新規actorがjoin → 全室のstatusが終了済みでもMATCHMAKING_FULL → 回収アラームが約60秒後へ延期された。

修正の方向：既存の早いアラームを後ろへ動かさず、回収期限と通常書込みを分離する。閉鎖済みと確認した部屋を満員判定から除く際も、参加枠の安全な解除条件を守る。

### R04 / P2 / 終了済み予約の回収後は、ログアウト成功でも旧tokenが有効【再現済み】

箇所：[Matchmaker.cancel](../../src/worker/matchmaking/Matchmaker.ts) 187行、[GameRoom.cancelReservation](../../src/worker/game/GameRoom.ts) 183–191行。

終端の回収では参加枠だけを外し、結果表示用のsessionsが残る。その後のlogoutはqueueにentryがないので成功を返すだけで、部屋のtokenを失効させない。

HTTP側でCookieを削除してもサーバー側の資格は残り、すでに接続した別タブや旧Cookieを保持する接続は取り消せない。R02とは別に、正しいlogout APIを呼んでも発生する。

再現手順：部屋をFINISHEDにする → resumeを使って終端回収を実行しNO_ACTIVE_MATCHを確認 → cancel(revoke=true)が成功 → 元のtokenで部屋に接続するとHTTP 101。

修正の方向：組織の参加枠が消えた後も、本人の指定部屋に対するログアウト失効を安全に行える契約を設ける。他人の部屋を失効させない本人照合も必要。

### R05 / P2 / 管理・閲覧への画面移動で、対戦用接続が切れる【コード確認】

箇所：[OrganizationGateway](../../src/client/features/organization/OrganizationGateway.tsx) 18行、[OrganizationPanel](../../src/client/features/organization/OrganizationPanel.tsx) 84行、[useGame](../../src/client/features/game/useGame.ts) 105行、[state](../../src/worker/game/state.ts) 354–395行。

インスタンス一覧・管理へのリンクは同じタブでページを移動し、現在のWebSocketを失う。2人対戦なら既存の復帰猶予（標準30秒）後にconnectionsによる無効試合となり、切断者に減点され得る。待機中も予約期限が進む。

「別画面を開いても予約は取り消されない」という表示だけではこの影響が分からない。

修正の方向：対戦接続を保持したまま閲覧できる構成か、別タブで開く明示的な導線を設ける。参加枠を維持することと、利用者が管理画面を閲覧できることの両方を受入試験に含める。実ブラウザーでの再現は未実施。

### R06 / P2 / 問題も設定もない新規インスタンスが「候補0件」として案内されない【コード確認】

箇所：[loadMatchDefinition](../../src/worker/catalog/database.ts) 82–89行、[Matchmaker](../../src/worker/matchmaking/Matchmaker.ts) 71–76行。

追加インスタンスはカタログをコピーしないので、初期状態には大会・出題設定の行もない。この状態ではNO_RANKED_QUESTIONSに到達せずDEFINITION_NOT_FOUNDになる。

修正の方向：未設定・候補0・DB接続障害を区別する。一般ユーザーには参加できない理由、運営には問題登録・停止状態・出題設定の確認先を表示する。

### R07 / P2 / 追加インスタンスのカタログを準備する標準CLIがない【コード確認】

### R08 / P2 / 権限の再読み込み後も古いチェック状態が残り、取消済み権限を再付与し得る【コード確認】

箇所：[InstanceGrants](../../src/client/features/organization/InstanceGrants.tsx) 23行・42–49行、[setInstanceGrants](../../src/worker/organization/database.ts) 238–246行。

修正の方向：取得済み権限と編集中の状態の同期規則を決め、権限の版などで古い更新を検出する。編集内容を無言で破棄する同期も避ける。

### R09 / P2 / 管理画面で権限付与先を本人と照合しづらい【コード確認】

### R10 / P2 / 1室のRPC障害が同じ固定版への新規参加全体を失敗させる【コード確認】

### R11 / P3 / 名称編集と保存後の再読込に、古い表示・誤った成功扱いがある【コード確認】

名称欄はdefaultValueで初期化され、同じインスタンスを再読み込みしても編集中の値が更新されない。別タブで名称を変えた場合、見出しと入力欄が食い違い、保存すると以前の名前へ戻せる。

修正の方向：編集対象の更新検知を行い、保存成功と最新表示の取得失敗を別々に扱う。

### R12 / P3 / 追加要求の重複防止が画面の寿命と現在の名称に依存する【コード確認】

箇所：[OrganizationPanel](../../src/client/features/organization/OrganizationPanel.tsx) 17行・138–151行、[addInstance](../../src/worker/organization/database.ts) 145–158行。

追加IDは画面内のstateだけに保持する。サーバーで追加成功後に応答が失われ、ページを開き直して再送すると新UUIDとなり、同じ意図のインスタンスを重複作成し得る。

修正の方向：処理結果を確認できる要求IDを復旧可能にし、追加要求の同一性を可変の表示名だけに依存させない。同名インスタンスを一律禁止する仕様変更とは分ける。

<details>
<summary>小さい懸念・追加検証が必要な点</summary>

以下はすべてを実害のある脆弱性と断定するものではない。後続段階の範囲に属する内容も明記した。

- **リクエスト制限の位置**：[organization routes](../../src/worker/organization/routes.ts)では認証後に本文サイズを確認し、組織API全般には回数制限がない。

  対戦経路もSupabase認証・組織DB処理・要求者の部屋照会を済ませてからMatchmakerの回数制限へ進む。認証済み利用者による大量要求に対し、高価な処理が先に実行される。実測と入口での上限設計が必要。
- **通常の参照要求もDBへの書込みになる**：[organizationIdentity](../../src/worker/organization/database.ts) 36–52行は毎回INSERT ON CONFLICTを行う。

  無効なinstance IDもその後で検証する。組織一覧も組織行を重複取得する。接続・クエリ数と競合を計測し、明らかに無効な入力の早期拒否などから整理できる。
- **一覧の全件取得**：一般ユーザーの一覧も全インスタンスを取り出してアプリで非公開分を落とす。管理者一覧は全アカウント・全権限を毎回取得し、画面はインスタンスごとに同じアカウント選択肢を作る。

  規模が増えた際の応答サイズ・ブラウザー負荷・grants.actor_id検索の索引不足を確認する。現時点で非公開情報がレスポンスに漏れることを確認したわけではない。
- **組織の待機列が単一の大きな値**：[Matchmaker](../../src/worker/matchmaking/Matchmaker.ts) 128行・261行はpendingに固定問題全体を含めてqueueを全体保存する。

  遅延中の予約が重なると容量と書込み負荷が増える。

  Cloudflareの公開仕様ではSQLite版DOのkey+valueは2MB上限：[公式制限](https://developers.cloudflare.com/durable-objects/platform/limits/)。

  今回の大容量ローカル試験では上限超過を確定再現できなかったため、「2要求で必ず落ちる」とは判断しない。ローカルで大きい値を書き込めたことだけで本番容量適合を保証しない。
- **結果原本と集計表の照合**：[commitResult](../../src/worker/results/database.ts)は原本とoutboxのhashを照合するが、成功済み結果の再送時にresult_playersとの一致は確認しない。

  専用writerには同表への追加INSERTが許され、payload中のplayersとの一致をDB制約で保証していない。

  通常の同一TXでは部分保存を防げているが、別の内部writerの不具合等で集計が原本とずれた場合の検知・再構築検証が必要。外部APIからこれを改ざんできることを確認したわけではない。
- **DB制約の粒度**：新しいname・subject・identity_namespace・actor_idはNOT NULL中心で、長さ・空文字・actor hash形式はDBで保証しない。

  RLSはサービスロール単位で全行を許可し、インスタンスごとの認可はアプリが担う。これは直ちに設計誤りではないが、運用SQLや将来の別writerが増える前に不変条件と信頼境界を明記する。
- **組織機能の無効化が従来経路を開く**：[instanceContext](../../src/worker/organization/handlers.ts) 50行以降はORGANIZATION_ENABLEDが厳密なtrue以外なら従来ownerを使う。

  移行済み配置で変数の欠落・誤字・設定の巻戻しがあると、準備中等の組織DB判定を通らない経路へ戻る。互換性のための切替自体は既定方針だが、有効化後の設定検証と切戻し手順が必要。
- **専用DB接続の実確認不足**：新roleはパスワード未設定で作られる。資格情報の発行・保存・実接続の手順がまだ揃っていない。

  ローカル検証スクリプトのSET LOCAL ROLEでは専用ログイン、TLS、Hyperdrive、実際の接続権限を検証できない。移行前に別途確認する項目であり、今の既存DBへ無断で資格情報を設定する理由にはならない。
- **候補0後の画面復旧**：[connection](../../src/client/features/game/connection.ts)はNO_RANKED_QUESTIONSで接続を止めるが、useGameのroomIdは残る。

  画面には閉鎖済み部屋への「再接続」が残り、再マッチングには待機取消等が必要。開始直前の最後の接続者は503で拒否されるため、既存接続者と同じ理由表示も受け取れない。部屋を解除した状態をUIへ明確に伝える必要がある。
- **運営向け案内不足**：候補0の案内は一般ユーザーと運営で同じ。「登録・承認・停止状態・出題設定を確認」の運営導線は準備中カードにしかなく、公開後の障害時に見つけづらい。

  第2段階の管理画面が完成していなくても、確認項目の表示は用意できる。
- **エラー診断**：[handleError](../../src/worker/http/handlers.ts) 21行のcorrelationIdは返すだけでサーバーログと対応していない。

  組織DBで失敗した結果APIがPROBE_FAILEDになる経路もある。秘密値を記録せず、経路・エラー分類・相関IDを追える仕組みが必要。
- **長期保持**：closed:<generation>・revoked:<token>の墓標と終了済み部屋の保持期限がない。すぐ削除すると遅延RPC対策を壊すので、許容再送期間と結果保存完了を踏まえた整理方針が必要。

  結果の法的・運用的な保持期間を今回勝手に確定するものではない。
- **公開・権限変更の監査**：現行の表には誰がいつ変更したかの記録がない。監査記録全体は第3段階の設計対象だが、実際に権限変更を運用し始める前に、現在の操作分を追跡する方法は必要になる。
- **文字入力と小さな表示不備**：validNameはCcを拒否するが、双方向制御等のCfは許容する。表示名等の制約は後続判断を含むので、類似表示・不可視文字を受入で確認する。通常対戦の表示名はさらに制約が緩い。

  共通コンポーネントやReactの文字列表示を使っており、今回XSSを確認したわけではない。
- **操作分岐の保守性**：[mutateOrganization](../../src/worker/organization/handlers.ts)は既知の接尾辞以外を公開操作として扱う。

  現行ルートだけなら直ちに利用者が任意のパスで公開できるわけではないが、操作追加時の誤接続を避けるため、公開操作も明示して未知を拒否する方が安全。
