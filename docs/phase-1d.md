## 第一段の実装範囲（2026-09-14）

正式ランクマッチの終了時に、終了理由・開始/終了時刻・固定ルール/セット参照・参加者状態・レート差分をDOへ固定する。未表示問題本文、正解、入力解答、cookieは結果原本に含めない。DB保存まで「保存中」、commit確認後のDO保存が済んだら「確定」。結果・参加者差分・outbox原本は同一TXで保存する。

初期1000、固定±20。通常勝者+20・敗者-20。引き分け0。ただし未復帰または失格は-20を優先し、二重減算しない。INVALIDは接続中かつ未失格だけ+20、その他-20。全員切断は全員-20。7問先取・3回失格・30秒復帰猶予は従来どおり。レートによるマッチングやEloは未実装。

ランキングは開催元GAME_OWNERの全期間の確定差分を直接集計するため、別の加算済みカウンターを持たない。レート同値は1,1,3方式。表示順だけactorIdで固定。カジュアル・部屋建て・開発参加はレート0でランキング対象外。現行の参加UIはランクマッチだけで、カジュアル/部屋建て機能は追加していない。

本人履歴は最新20試合、順位は上位100人。正式認証とOrigin検証を必須にし、actorは検証済みAuthから導出する。保存失敗時は空の順位で成功したように見せず、再読込を案内する。

## 保存と復旧

- 同じresultIdで再試行。owner/matchIdにも一意制約。同じIDの異なるhashは競合表示として停止し原本を保持する。
- DBへの書込み前にDO原本と次回Alarmを保存。DB待機は直列化区間外。再接続やsyncで再試行予定を延長しない。
- 再試行はconfig/runtime.jsonのresults.retryIntervalMs（初期30秒）。DBが停止中でも回数超過で破棄しない。結果を保持する各DOに1件の再試行予定を持つ。
- commit後に応答が失われても、同じ内容の存在確認で確定する。終了後の接続状態変更で原本・レートを再計算しない。
- 開始時刻やmatchKindのない旧DOと開発参加はDB保存・レートへ遡及しない。
- result_outboxは原本の保存準備。宛先・外部配送・署名契約・inboxは2C。UIで外部同期済みと表示しない。

## ローカル操作

1. 既存DBでは適用済みの0000〜0004を再作成しない。今回は0005〜0007をDrizzleで適用済み。新環境は通常の `pnpm db:migrate` を使う。
2. .dev.varsのRESULT_DATABASE_URLへquiz_game_resultsの専用接続を設定。この作業環境では設定・接続確認済み。秘密をチャットやGitへ書かない。readerや管理者の接続を代用しない。
3. `pnpm dev` を起動し、/game/で正式ログインしてランクマッチに参加する。すでに起動中なら新しいbindingを読むため再起動する。
4. 終了時に各自の±20と「保存中→確定」を確認。確定後に履歴・順位を再読み込みする。DB停止時は保存中のまま、復旧後のAlarmで確定する。
5. 同じ試合へ戻っても結果・レートが増えないことを確認。引き分け・失格・未復帰・INVALIDは上記条件どおり。

`config/rating.json` は承認済みv1の識別情報（1000/20）。変更値を自動採用せず検証で拒否する。レート制度変更時は既存原本との互換性・版移行を決めて実装する。将来の管理UIから変更できる人数・競技ルールとは分ける。
