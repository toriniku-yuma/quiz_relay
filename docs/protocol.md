## 参加チケット

1. BでSupabase Authの本人確認を行い、B APIがユーザーの所属actorを確定する。
2. Bが署名チケットを発行する。必須claimは `iss, sub, aud, matchId, jti, iat, exp, protocolVersion`、TTL初期案は60秒。メールは含めない。
3. ブラウザーはチケットをAへHTTPS POSTし、Aは署名、pin済みkid、iss、aud=A、matchId、期限、peer状態を検証する。
4. Aは `(iss,jti)` を永続ストアで原子的に消費し、開催元の参加セッションを作る。同時交換は1件だけ成功する。

## 署名・正規化案

署名はEd25519のJWS、algは固定allowlistとし、チケットと連合メッセージで用途を分離する提案。実行環境・採用ライブラリの互換性と公式仕様を確認してADRで確定する。独自暗号処理は実装しない。

連合HTTPはJSONで `{ "message": "<compact JWS>" }` を送る案。署名対象payloadに `protocolVersion, messageType, issuer, audience, issuedAt, expiresAt, nonce, method, path, bodyHash, body` を含める。bodyHashとrulesHashはRFC 8785のJSON正規化後のUTF-8をSHA-256しbase64url化する提案。重複JSONキー、非有限数、規定外の型を拒否する。署名は受信したJWS signing inputを検証し、bodyを再正規化してhashも確認する。

配送イベント本体も発行者署名付きで保存し、永続イベントの署名と有効期限の短い配送署名を分ける。再送ではeventIdとイベント本体は不変、配送nonce・発行時刻・署名だけ更新する。期限切れ配送を受理して過去イベントを回復する運用にはしない。取消も同じ封筒を用いる。

受信順序はサイズ制限→JSON/JWS構造→承認origin/kid/alg→署名→宛先・用途・method/path→時刻→本文hash→nonce→本文スキーマ・権限。HTTPヘッダーを信頼の根拠にしない。署名不正はDB投影に到達させない。

初期の上限案：配送TTL 60秒、時計許容差5秒、通常イベント256KiB、問題セット2MiB。レート制限とnonce保持時間はsecurity.mdと合わせて確定する。過去イベント検証用に旧公開鍵と承認履歴を保存し、現行鍵の期限と過去署名の監査可能性を混同しない。

## 受領、再送、収束

inboxは `(origin,eventId)` を一意にする。同じID・同じhashは重複成功、同じID・別hashは409と隔離。新規イベントは署名原本と検証情報を永続化して202、重複は200を返す。受領成功は順位反映完了を意味しない。

outboxは宛先単位でattempts、nextAttemptAt、lease、最終エラー、状態を保持する。指数バックオフとjitter（1秒〜15分を初期案）、429のRetry-Afterを考慮。通信断・5xx・429は再送、仕様違反・認証エラー・409は隔離して管理者が修正後に再送する。peer停止は配送を保留し、再承認後に再開する。回数超過だけで未配送結果を破棄しない。

再送の起動とlease失効でプロセス停止から復帰する。受領側は未投影イベントを再処理可能にし、投影失敗を受領済みだからと取りこぼさない。エラーは `{code, retryable, correlationId}` 形式とし、秘密や入力解答を返さない。

## 1Cの同一開催元向け参加API（2026-09-14）

連合チケット交換は2A。以下は実装済みのローカル所属ユーザー向け経路。更新APIは同一OriginとSupabaseで検証したBearerを必須とする。本文は最大1024bytes、未定義フィールドを拒否する。

| メソッド・パス | 本文・認可 | 応答 |
| --- | --- | --- |
| GET /api/auth/config | 公開 | url・publishableKeyだけ、no-store |
| POST /api/matchmaking/config | Bearer | competition参照・playersPerMatch・rules。問題内容は含めない |
| POST /api/matchmaking/join | Bearer、{name} | {room}とHttpOnly cookie。二重参加409 |
| POST /api/matchmaking/resume | Bearer、{} | 同じactorの{room}とcookie。参加なし409 |
| POST /api/matchmaking/cancel | Bearer、{room} | 待機だけ取消。開始後409、古い部屋指定409 |
| POST /api/matchmaking/logout | Bearer、{room} | 本人の部屋セッション・接続を失効 |
| GET /api/matchmaking/socket?room=UUID | 同一Origin・部屋cookie・WebSocket Upgrade | 1Bのstate/delta/ackと本人用panel |

初回セッションは認証済みsubjectと開催元から導出したactorへ結び付け、cookieはSecure/HttpOnly/SameSite=Strict、path=/api/matchmaking、最大12時間。tokenはURL/JSONに含めない。WebSocketでは部屋cookieを認可し、初回のBearerを再送しない。ログアウト操作で失効するが、Supabase管理側の失効が既発行cookieへ即時伝播する方式ではない。

正式部屋は1c:<UUID>。Matchmakerが開催元全体の二重参加を防ぎ、GameRoomは設定人数の異なるactor接続がそろった時だけDB固定版を再確認して開始する。取消と開始は同じDO内で直列化。未接続予約60秒・待機部屋10分・セッション12時間の期限を復帰で延長しない。開始後の切断猶予・終端状態・再送/復帰は[1B手順](phase-1b.md)に従う。

2026-09-14：config応答のrulesはDBで検証した公開ルール値。設定切替後の新規参加は新しい大会版を使用し、既存部屋は保存した版を保持する。正解数の目標到達によるDO結果理由は `target_reached`。旧保存データの `seven_correct` もクライアント表示互換のため受け付ける。これは1DのDB結果確定・2A以降の連合契約の完了を意味しない。上記の予約・待機・セッション時間はconfig/runtime.jsonの初期値。

2026-09-14レビュー修正：新規参加のDB読込失敗は503 / GAME_DATABASE_UNAVAILABLEを返し、cookieを発行しない。同一actorの後発要求・取消等で古くなったDB読込結果は409 / STALE_REQUESTで拒否する。DB読込は開催元の直列化区間外、予約の確定は最新状態を確認した直列化区間内で行う。1リクエストの回数加算はDB読込前の1回だけ。

## 2026-09-14：1D第一段の変更

結果保存・レート・履歴を実装。従来の総得点順位・INVALID全除外案は、[仕様書](specification.md#ランキング2026-09-14承認)のサーバー全体レートへ置き換える。失格・未復帰の減少を優先し、INVALIDでは接続中かつ未失格だけ加点。部屋建て・カジュアルはランキングに影響しない。

結果原本・参加者の固定レート差分・配送準備用outboxを同一TXで保存。resultIdとowner/matchIdを一意にし、再送は内容hashを照合。不一致は上書きせず競合表示。DB待機をDO直列化区間の外へ出し、未保存原本と再試行Alarmを先に永続化する。旧DOの過去結果には遡及しない。

1Dのoutboxはローカル原本を保持する準備であり、宛先別配送・署名付きresult.finalized・inboxの完成ではない。INVALIDの外部通知を含む連合契約は2Cで確定する。専用writerのRESULT_DATABASE_URLをローカルで使用し、reader・設定writer・migration管理者を維持する。詳細と未実施は[1D手順](phase-1d.md)。
