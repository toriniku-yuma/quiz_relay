## 担当と進め方

「画面受入」は開発担当がブラウザーで先に確認できる。ユーザーには使い勝手や仕様判断を確認する。「技術試験」は開発担当が実施し、単に手作業で試すだけでなく、再現可能な自動試験を優先する。「環境確認」は設置者の接続設定・対象環境の情報が必要になる。

推奨順序は **UI-01〜07 → DEV-01〜03 → UI-08〜12 → ENV-01〜06 → 移行実行の確認**。回答待ちの仕様や後続段階の保持方針を理由に、独立した確認を止めない。

下の表は元の合格条件を保存したもの。最新状態は冒頭の9月18日表を優先する。各項目の状態は初期値「未実施」。実行後に「合格／不合格／一部確認／対象外」を記録する。該当画面が未実装の場合は「不合格」ではなく、未実装・仕様待ちとして記録する。

### 画面確認を始めるための準備

- 専用の検証DB・Worker設定・Authを用意する。`pnpm dev`であっても接続設定次第で既存DBに届くため、起動前に接続先を確認する。Dockerは不要。
- 初回設定用の空DBと、設定済みの検証データを使い分ける。既存環境を初期化して試さない。
- 管理者、対象インスタンスの担当者、権限のない一般ユーザーを別ブラウザープロファイルで用意する。対戦成立に必要な人数も用意する。
- 公開中A／公開中B／準備中Cを用意し、出題設定未登録、候補0、正常な出題設定を専用データで再現する。第2段階の未実装管理画面を前提にせず、必要な準備は既存CLIを使う。
- 同一ユーザーの複数タブと、別ユーザーのプロファイルを区別する。ブラウザー名・版、画面幅、対象URL、コード版を記録する。
- 秘密値、Bearer token、Cookie、DB接続文字列を証跡へ貼らない。スクリーンショット・通信ログは必要箇所だけを残す。
