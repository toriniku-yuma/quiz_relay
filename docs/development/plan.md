## DB・認証の範囲・完了条件

ゲームDBはCloudflare D1、認証はClerkのGoogleログインです。早押しの裁定・接続・進行中の状態管理にはDurable Objectsを使います。D1の76テーブル・migrationと、組織・権限・運営・作問・審査・部屋・結果・カタログ・退会・完全削除・復旧・保存期限の処理を実装しています。難易度は完了試合の追加集計と、件数制限付きの日次判定で更新します。通常API・管理ツール・消去Worker・定期処理は同じD1を使います。ClerkのDevelopment実アプリ設定、Chromeでの実Googleログイン・本人確認、待機参加・画面移動での接続維持・取消を確認済みです。実DOからD1への結果保存と通常履歴APIも隔離環境で確認済みです。公開A/Bの通常ゲーム・非公開消去Worker・Cronを配置し、実Google認証で外部ランク・部屋対戦・外部履歴・開催元の振り返りと、問題共有の取り込み・検索・個別除外を確認しました。ローカル・公開A/Bの仮想利用者による30分継続試験は完了しています。本人による退会とiOS Safariの実機受入は未確認です。[検証範囲](testing.md#d1-clerk)を参照してください。

- DrizzleでD1の接続・SQLiteスキーマ・migrationを管理する。別DBへ切り替えるためだけの汎用層は作らない。
- 認可はWorkerで行い、整合性はD1の制約・トリガー・原子的なバッチ、更新条件の照合で守る。結果・参加者・配送原本の同時保存、重複排除、改変防止、退会・完全削除を維持する。競合・再送・途中失敗で一部だけ反映されないことをD1で検証する。
- アカウント認証はソーシャルログインに限定し、Googleを使う。メールリンク・メールコード・パスワードによる認証は提供しない。Clerk側の設定でも制限し、画面から隠すだけで済ませない。認証に不要なOAuth権限を要求せず、認証トークン・メールアドレス等を通常ログへ出さない。
- ローカルはD1のローカル実行環境、公開検証は無料プランを使う。2組織のWorker・D1・Clerkアプリを分離し、同組織内には各2インスタンスを用意する。Chrome・iOS Safariで認証・参加・再接続・退会を確認する。Clerk本番環境に必要な管理可能ドメイン・DNS・Google OAuth設定は保有状況を確認し、購入・有料化は別途判断する。
- 問題の取得、結果保存、難易度判定、連携の同期・再送について、読み書き行数・保存量・実行時間・通信量を測定する。無料枠の超過を避けるため件数制限と再開位置を持ち、過去結果や配送原本の削除で容量を合わせない。

難易度は初期値を自動で対応付け、運営が補正・固定できる方式を基本にします。実績による更新は既存の日次判定条件を使い、新しい実績がある問題だけを件数制限付きで処理します。全履歴の定期的な再走査や、難易度判定のためだけの組織間通信は追加せず、実測した負荷と運用結果に応じて処理頻度・上限を調整します。共有問題の元情報・開催先での推定値を分け、通常の同期で開催先の補正を上書きしません。

## 組織・インスタンス基盤の完了条件

具体的な構成は[組織設計](../design/organization.md)を参照します。

1. 初回起動で管理者を設定できる。
2. 管理画面から複数インスタンスを追加できる。
3. 同じアカウントで各インスタンスを利用できる。
4. モデレーター権限・問題・レート・待機列・部屋が混ざらない。

非公開中も組織管理者・対象インスタンスの管理権限を持つモデレーターが通常対戦へ参加できることを確認します。専用テスト対戦・専用履歴は作りません。

分離の確認を理由に、後続段階の作問審査や部屋の全機能までこの段階に前倒ししない。新機能は追加時にも分離を確認する。

## 作問・審査・出題の範囲・完了条件

- 作問フォームとJSONの複数インポートから問題を登録し、本人の問題をJSONでエクスポートできる。
- 類似問題の増加を防ぐため、管理者・作問管理モデレーターが管理対象の問題文・表示用正答・読みを検索し、カテゴリ・タグ・状態で絞り込める。

  審査中・公開中・停止中を検索でき、審査中の問題と既存問題を並べて比較し、審査者が重複を判断できる。
- 4種類の投稿方式、担当権限、管理者だけの自己承認に従って審査でき、承認・理由付き差戻し・理由付き却下を画面で処理できる。
- 改訂中の旧版利用、使用停止、資格取消時の審査打切りを確認できる。
- 複数読み・ひっかけを登録し、対戦で最初に登録済み正解読みへ到達した時点で正解になる。候補不足はダミー補充する。
- カテゴリ・タグ・難易度・カテゴリ変更・通報／再審議を既決仕様に従って管理できる。確定した難易度設計を含めて受入検証する。
- タグは同じインスタンスの既存候補を表示し、新規作成できる。運営が同義タグを統合・別名登録し、旧名でも検索できる。類似語は自動統合せず、初期は階層化しない。
- タグ検索は作問者には自分の問題、管理者・作問管理モデレーターには管理対象の問題に限定する。統合・別名登録は管理者・作問管理モデレーターが行う。一般プレイヤーに表示せず、出題条件に使用しない。
- ランクで利用可能な問題からカテゴリ割合に従って自動出題し、結果で出題済み問題を振り返って通報できる。未出題問題や一般非公開の審査情報を公開しない。
- ランクの出題候補0件なら新規受付・試合開始を止め、理由表示とともに待機解除する。運営画面で確認箇所を案内する。

  開始済み試合は固定済み候補で継続し、候補0の検出と試合開始の競合でも開始済み試合を取り消さない。
- 候補復旧時：利用可能な出題候補が戻れば、候補0件を理由とする受付停止を自動解除する。解除済みの待機者は自分で再参加し、自動で待機列へ戻さない。管理者の手動休止は解除しない。

  公開状態・モードの有効設定・個別参加制限等も引き続き適用する。

## 運営・モデレーションの範囲・完了条件

- モデレーターの権限設定、タイムアウト・BAN・部分制限を画面から行える。インスタンスBANと組織全体BANを区別し、試合中の処分は次試合から適用する。
- 権限内で過去の戦績を調査でき、審査結果や処分等をサイト内で通知する。
- ランク・カジュアルマッチを個別に停止・再開できる。作問も含むインスタンス全体の休止は準備中への切替で行い、再公開できる。全体休止と個別停止の設定を独立して維持し、どちらの停止中も組織管理者・対象インスタンスの管理権限を持つモデレーターは通常対戦へ参加できる。
- 管理者が後任を指定し、本人の承諾を経て引き継げる。
- インスタンスのアーカイブと権限に従った問題エクスポート、対象名入力による完全削除を行える。退会者の通常表示を隠しつつ、投稿問題・相手の戦績・必要な調査記録を保持する。

カジュアルマッチ・部屋への参加制限・休止・退会・削除の接続、持込問題・ゲストの30日保持は部屋段階で実装・検証しています。組織間連携の参加制限と共有先への停止通知も実装済みです。本番適用・実機での受入は実装完了とは別に確認します。

## カジュアルマッチ・部屋マッチの範囲・完了条件

- レート変動なしのカジュアルマッチを利用でき、インスタンスごとに有効・無効を設定できる。
- 公開部屋は一覧から、非公開部屋は招待から参加できる。
- 部屋ごとに人数・出題カテゴリ・勝利条件を設定できる。
- 簡易作問フォームとJSON読込でオリジナル問題を持ち込み、作成者だけが保存・再利用できる。
- 設定に従ったゲスト参加、途中参加者のロビー待機、部屋主の退室・切断時の入室順での交代、結果確認・再参加まで行える。
- 問題不足時の勝敗、運営機能の参加制限・休止を確認する。16人対応は必須条件にせず後回しにできる。

詳細は[部屋仕様](../spec/rooms.md)を正とし、任意パスワード・招待再発行、難易度、2〜8回答者と専任／兼任、準備完了・部屋主開始、切断復帰・途中入室、作成者だけの編集・出力・削除、振り返り・通報、組織共通の同時参加制限も含めます。結果原本は試合ごとに固定し、保存・再試行・再接続・次試合で失わず、レート・全ランキング・ランク難易度集計へ混入させません。ゲストは個人通報の対象外です。
追加の参加・UI調整として、ゲストの直接URL、ランク人数の管理画面、サーバー内1枠と明示的な離脱後の参加、ランク強制離脱の-20、対戦専用ページ、同モードの開始済み試合だけの復帰案内、認証の回転アイコンとフェードを含みます。候補登録・画面移動でも参加処理・自動待機・部屋ロビーを保持します。自動待機は本人の取消・最後の接続切れで解除し、別タブが接続中なら切断だけでは解除しません。履歴とランキングを個別ページに分け、履歴は種別絞込・20件ずつの追加取得・本人だけの詳細と振り返りを提供します。既存フェーズの実装と追加UIのブラウザー受入は別に確認します。

この範囲は実装済みです。確認した層と未実施の受入・性能試験は[検証状況](testing.md#カジュアルマッチ部屋の実装検証)で区別します。共有問題の選択・許諾・取得・停止通知と別組織参加も実装済みです。16回答者は任意拡張です。

## インスタンス間連携の範囲・完了条件

外部参加・問題共有・結果配送・停止と匿名化通知・外部お気に入りを実装しました。公開A/Bの構成は通常ゲーム・非公開消去Worker・毎時と日次のCron・別D1・別Clerkアプリ・署名鍵です。各側に1組織・2インスタンスを用意し、実Googleで外部ランク・部屋対戦・結果・外部履歴・振り返り、問題取り込み・検索・個別除外を確認しました。実装・隔離試験・公開Chrome・実機・継続負荷を[検証状況](testing.md#d1-clerk)で区別します。[検証環境](../guides/setup.md#federation-test)に再配置手順を記載します。

- 外部参加は所属組織のアカウントで行い、参加元インスタンスを選ばない。開催元は組織全体の受入方式と相手組織ごとの対戦種別を設定できる。問題共有は相手インスタンスごとに送出・受入を設定し、同じ組織内でも個別にする。結果は参加記録に結び付けて所属元へ配送し、共有設定を設けない。同組織内の共通ユーザー参加は外部参加扱いにしない。
- [外部インスタンスのお気に入り](../spec/federation.md#外部インスタンスをお気に入りに追加する)を実装する。お気に入り一覧を中心にし、新しい先はインスタンスURLで開く。承認済み一覧は必要時だけ表示し、本人が個別に追加・解除して別端末でも利用できる。登録と接続先の承認・参加許可を分け、直接URLからの自動追加をせず、画面移動と登録変更でも現在の参加・接続を維持する。
- 別組織からの参加をランク・カジュアルマッチ等で制御でき、個人への処分も適用される。
- 所属元の一覧・URLから開いた開催先では自動本人確認し、通常の対戦画面・共通サイドバーへ統合する。閲覧だけで参加せず、開催先の会員登録を別導線にして優先する。ログアウトは開催先だけ終了し、ゲストへ戻って自動再ログインしない。
- 問題共有はインスタンスごとの送受信許可と使用停止を反映し、カテゴリ別の公開設定は設けない。部屋では共有元ごとに使用可否を選べる。共有解除・取得失敗時は新しい試合で使わず、進行中の試合は開始時の内容を維持する。
- 複数の共有元の全カテゴリ／選択カテゴリを、通常または取り込み専用カテゴリへ保存できる。複数元の集約と、カテゴリ別の複数保存先を扱い、元の分類・共有元情報を保持する。取り込み専用カテゴリへの通常投稿をAPIでも禁止する。
- 難易度を簡単・普通・難しいに固定し、対応表を設けない。受け取り先の自動補正と管理者の固定値は通常同期で維持する。
- 全問題で通常問題と共有問題を横断検索し、共有元・保存先・除外状態で絞り込める。問題の操作から除外・解除でき、再同期・共有元の改訂後も除外を維持する。常設の再取得・手動同期ボタンは置かず、相手への取得を回数・件数を制限した定期処理で行う。

  解除しても共有元の停止等の利用制約は維持する。他の共有先・共有元・進行中・過去結果への影響と、一般利用者への未出題問題・正答の漏洩がないことを確認する。
- 別組織で遊んだ結果を本人の履歴から確認し、開催元で振り返れる。レートは開催インスタンスごとに分ける。
- 問題取得・結果配送の失敗を運営画面で確認し、復旧できる。

| 組織間連携・共有問題設定（`FederationPage`、`FederationPolicies`、`QuestionSharingPage`、`QuestionImportForm`） | 設定、相手インスタンス、共有元カテゴリの取得 | 選択に依存する候補の取得に限定し、フォームを保持する。別の相手・共有元の候補を新しい選択の結果として表示しない |
| ランク・カジュアル・部屋の入口（`MatchPage`、`CasualPage`、`RoomsPage`、`OrganizationGateway`、`GuestInstances`） | ログイン・参加状態・ゲスト参加設定の確認 | 共通情報の重複取得を見直し、確認対象付近に回転アイコンを置く。進行中の参加・接続を維持する |
| 部屋一覧・ロビー・自分の問題セット（`RoomWorkspace`、`RoomLobby`、`PersonalSets`） | 一覧・組織情報・ロビー・保存済みセットの取得 | 一覧と操作欄を先に表示できるか確認し、更新・接続待ちは対象内に限定する |
| 外部ログイン・参加認証（`ParticipationAuthorizationPage`） | ログイン・所属組織の確認 | 必要な本人確認は維持し、回転アイコンと確認内容を表示する |
| 対戦接続・再接続（`MatchLobby`、`ForeignGame`、`GamePage`） | 接続確立・復旧待ち | 対戦画面や進行状態を保持し、接続待ちを局所表示する。対戦相手待ち・出題待ちとは区別する |
| 開発用画面（`ConfigurationPanel`、`ResultPanel`） | 設定取得・検証リクエスト | 通常画面と分けて確認し、実行中の対象に待機表示する |

実施内容と完了条件：

- セレクト変更だけで完結する入力に通信・読み込み表示を発生させない。保存や検索が必要な操作は既存の操作契約を保ち、不要な再取得・再マウントを除く。
- 初回は見出し・ナビゲーション・入力欄など表示可能なUIを先に出す。同じ対象の再取得では保持できる表示と入力を残し、待機表示は必要な領域に絞る。選択した条件と表示結果が一時的に異なる場合は、更新中であることを明示する。
- 残る待機表示は既存の `Spinner` を基本に、場所に合う大きさ・配置へ整える。短時間の処理での点滅、文章とアイコンの重複、不要な全画面オーバーレイを減らす。単に表示を隠すだけで通信削減済みとは扱わない。
- 取得失敗・空データ・保存中・再接続中を区別し、失敗後に回転し続けない。エラーと再試行導線を維持する。取得失敗を空データや成功として扱わない。
- 読み上げ用の状態説明と動きを減らす設定に対応し、キーボードのフォーカス・選択値・未保存入力・スクロール位置を不用意に失わない。
- 通常回線・低速回線・取得失敗で、初回表示、再訪、連続した選択変更、保存後、追加取得を確認する。変更前後の通信回数とUI表示までの時間を比較し、遅れて届いた応答による選択結果の巻き戻りや、別ユーザー・別インスタンスのデータ混入がないことを確認する。

### 予期しない切断と500の原因調査

500の原因調査も受入確認に含め、原因未特定の事象は記録を保持する。9人の部屋ロビーでホスト以外の8人を意図的に切断した直後、検証用の部屋APIが500を返し、維持していたホスト接続も切れた事象を対象とする。ランク対戦を並行実行していたが、因果関係は未確定。

診断ログは検証環境へ反映済み。過去のローカル・公開A/Bの30分継続試験で全参加者の結果保存・配送・切断復帰を確認したが、元の500の原因が解消したとは扱わない。診断拡張後の追加試験でも、DOのコード更新に伴うリセットの500で途中停止した。ライブ監視の内部再接続から約5分後にロビー全接続の切断が繰り返され、後の切断はこの500と一致した。監視がDO更新を誘発した可能性を検証するため、監視なしの試験と分けて評価する。個別の自然切断の原因は未特定。試験の失敗と復旧の状況は[残る受入確認](testing.md#d1-clerk)へ集約する。

- サーバーログ・クライアントの診断を使い、処理段階・例外分類・部屋を管理するDOの識別子を照合して、500とホスト切断の原因を調べる。ライブ監視自身の再接続やログ欠落も確認し、監視なしの比較ではクライアント記録と保存ログを使う。
- 原因を特定したら必要な修正と回帰検証を行い、復帰・対戦継続・結果保存を確認する。再現しない場合は試行条件と未解決の範囲を明示する。低頻度で復帰・結果保存・配送を確認できる事象はログで追跡する。試験停止、復旧期限超過、結果不一致、未配送の継続があれば、低頻度だけを理由に確認を終えない。
- 自然切断後の409について、部屋主交代後の専任再選択が試験手順に欠けていたことと、準備操作の所要時間で復旧期限を消費していたことを修正した。9人部屋での主交代・専任再選択・次試合完了は実環境でも確認済み。終了時刻を過ぎた新規開始も抑止し、時間管理を自動テストで検査する。切断復旧と全参加者の結果照合を含む30分継続はローカル・公開A/Bで確認済み。D1原本・所属元配送の一致とライブ配信の成功を分けて検証する。
- 自然切断自体の原因と元の500との関係は未確定。切断時に心拍期限超過・500・例外を伴わない事象もあり、アプリや実行環境のどちらが原因かを断定しない。接続の復帰成功だけを次試合への復帰成功とは扱わない。
- 強制切断前に起きた外部参加APIの503は別件として扱い、この調査の後回しに含めない。
