## 開発環境での対戦検証

非公開中の管理権限者による通常対戦はサービスの機能です。通常の結果・レートへ反映します。
開発環境の検証用データの分離は、その通常利用とは別です。開発検証はユーザーへ提供する機能ではありません。準備中インスタンスの運営者向けテスト入口や専用履歴・30日保持は設けません。

- 2〜4人で、設定人数の認証・接続・問題の準備が揃ったら自動開始する。準備完了・運営者の手動開始は不要。
- 通常の出題条件に従う。審査ありなら承認済み、使用停止されておらず、対象インスタンスの出題設定に含まれる問題を使う。共有問題は共有許可・取得成功も必要。
- 審査中・公開前の問題を試す専用機能、CPU・単独プレイは追加しない。
- 検証用データを本番のレート・正式な難易度集計へ混入させない。開発側の実施記録と、ユーザー向けの対戦履歴を区別する。

認可・停止状態などを確かめる自動テストのfixtureは、実際の対戦へ出す問題とは別です。
部屋マッチの準備完了・部屋主による開始は別機能であり、この開発検証の決定では変更しません。

## 部屋の大人数対応

部屋は8回答者＋出題専任1人を必須範囲として、機能・画面・認可・結果を検証する。16回答者は将来拡張であり、今回の完了条件に含めない。

回答者上限は8人です。ランク／カジュアルマッチの最大4人とは別に検証します。

実DOで8回答者＋専任者を確認します。16回答者の拡張時には再度検証し、32人対応は対象から外します。

- 同時早押し・連打・重複送信でも回答権と裁定が一意で、保存後ACK・文字期限・終端状態を維持する。
- ACK・パネル表示までの遅延、本文表示の遅れ、配信量・CPU・保存サイズ・エラー、切断復帰・DO復帰・連続対戦を確認する。
- 出題役専任・ロビー待機者・複数タブを含む総接続上限は、回答者数とは別に決めて検証する。
- スマートフォンで問題文・回答操作・自分の成績を確認でき、大人数表示で操作が埋もれないことを確認する。
- 応答時間の許容値・試験時間・同時部屋数・対象端末・予算は実施前に決める。

上記の継続負荷・遅延計測と実機試験は未実施です。実装した8回答者＋専任者の正しさ・復帰・保存・非公開境界は、次の実装検証で確認しています。本番適用・デプロイは行っていません。

### デザイン・効果音の確認

初期実装では、素朴なフラットデザインと装飾を抑える方針に沿っていること、回答ボタンが凸状に見え、押下時に沈み、押下不可とフォーカスが判別できることをタッチ・キーボード操作で確認する。

同梱された基本効果音が対象イベントで再生されること、オン・オフと音量が反映されること、ミュート・音源欠落・再生拒否でも入力や進行を妨げないことを確認する。

検証用設定はユーザーの本番用割り当てとして残さない。音がなくても正誤と進行状態を読み取れることを確認する。現時点ではいずれも未実施。

<a id="verification-021"></a>
## 発表シナリオ

1. A/Bのorigin、独立DB/Auth/鍵、機能別の連合許可と開催元別レートを示す。
2. A/B所属プレイヤーでA開催の対戦を行う。
3. Aで確定結果とAのレート、共有許可されたBで本人履歴と開催元表示を確認する。Bの通常レートは変動しない。
4. 同期先を停止して別試合を確定し、保存完了と同期待ちの違いを示す。
5. peerを復旧し、滞留結果が反映されることを示す。
6. 同じ結果を再送しても履歴が重複せず、開催元のレートが二重反映されず、所属元の通常レートが変わらないことを示す。
7. 取得停止・配送復旧の条件と、未確認の範囲を説明する。

<a id="verification-022"></a>
## 計測と記録

実行日、commit/lockfile、クラウド構成・地域情報、端末とブラウザー、同時ルーム数、人数、RTT、切断率、裁定遅延、DB保存時間、同期時間、試行回数、失敗と復旧を記録する。

遅延は測定区間を明記し、可能なら中央値とp95を残す。負荷上限・無料維持・地理的公平性を未測定で断言しない。

実測結果はこの文書の条件と分けて `docs/history/verification.md` 等に実施時点で追加する。開発基盤・外部接続検証のローカル基盤について検証記録を作成した。ゲーム・クラウドの動作実績とは区別する。

<a id="verification-023"></a>
## 認証付き対戦：設定変更の検証

- JSONの人数・ルール・型・未知キー・欠落・範囲外を検証し、不正設定を拒否する。
- 設定した正解数で勝利し、既存試合のルール・終了結果は変更しない。
- 有効プロファイルから新規参加を作成し、既存部屋の開始前確認は固定参照を使う。
- 実DBで設定反映SQLを2回実行し、版の重複生成がないこと、参照と人数・ルールが一致することを確認する。検証用変更はTXでrollbackする。
- 設定参照テーブルはreaderでSELECT可・UPDATE不可を確認する。クラウド配置と管理UIは別途。

<a id="verification-024"></a>
## Drizzle移行の回帰確認

`pnpm run check` と、明示実行の `pnpm db:check`・ローカルWorker実DB試験を使う。

新規版作成のrollback、同じ設定の再適用と別接続同時反映、reader/writerの拒否、管理者にも働く不変トリガーを検証する。migration再適用が無変更、Kitがスキーマ差分なしを返すことを確認する。

新規DDLは隔離スキーマで全statementをTX実行してrollbackし、既存環境と区別して記録する。

<a id="verification-025"></a>
## 設定検証とDB待機の競合

標準JSONをモックして必須9項目の各欠落と未知キー追加を拒否することを確認する。DB応答を保留した状態で別actorの復帰・取消・Alarmを実行し、DB返答を待たず完了することを確認する。

同一actorの後発参加と取消、DB失敗時の回数保持と503/cookieなしも検証する。

<a id="verification-026"></a>
## 結果保存とレート

[結果保存設計](../design/architecture.md)に従い、D01/D02はDOでの障害注入と実Postgresのcommit・別接続同時再送を分けて検証する。

D04/D06〜D08は承認済みレートへ期待値を更新。INVALIDの全指標除外という旧期待値は廃止する。カジュアルマッチ・部屋建ては0、通常敗者-20、引き分け0、失格・未復帰の減少優先を確認する。

D05は専用writer/readerの実接続による拒否、anon/authenticatedの権限設定検査、本人履歴APIのOrigin/認証/actor固定を確認する。作問管理画面と効果音は未実装です。

### 履歴の再読み込み競合

手動要求を保留して結果確定時の自動要求を先に完了させ、後着の古い成功・失敗で最新表示を上書きしないことを確認する。古い要求の完了で最新要求のbusyを解除しないこと、effect cleanupが手動要求も取り消すことを確認する。

<a id="verification-028"></a>
## 管理操作の検証

F08/G14/D05の管理CLI範囲として、問題改訂と停止の原子性、停止問題のセット作成/設定反映拒否、旧版保持、ルール/人数変更の新版作成、開催元のRLS、原本の変更拒否を実DBで確認する。

管理入力の未知キー・同一ID改訂・重複セットID・候補不足・所有者不一致をローカルテストする。手順は[catalog-management.md](../guides/catalog.md)。効果音とブラウザー受入は引き続き残件。

<a id="verification-029"></a>
## モデレーションと対戦休止の受入

- 個人処分・サーバー全体休止・外部全体／特定所属元の受入を画面と認可で区別する。
- 専用パーミッションの有無、管理者／運営者への操作境界、本人への理由表示とサイト内通知、非公開の運営履歴を確認する。
- タイムアウトの期限前後・早期解除とBAN／部分制限の手動解除を確認し、一つの解除で別の有効な処分が消えないことを確認する。
- 対戦機能の個別停止は一般ユーザーの新規参加・開始を拒否し、組織管理者・対象インスタンスの管理権限を持つモデレーターは通常参加・待機・開始できる。他インスタンスだけの権限では参加できず、他の対戦種別・作問には影響させない。
- インスタンス全体休止（準備中）は一般ユーザーの新規対戦・作問を拒否し、対象の管理権限者は通常機能を利用できる。他インスタンスだけの権限では利用できない。
- いずれの停止も開始済み試合・再接続・結果保存を維持する。再公開しても個別停止を解除せず、権限と公開状態をAPI直接アクセスでも検証する。
- 外部全体禁止と先別許可、外部許可と個人BAN、自サーバー所属者と外部受入設定の組合せを確認する。所属のないゲストを自サーバー所属と誤認しない。
- 個人処分は次試合から適用し、既存試合の継続・再接続を妨げないことを確認する。ゲスト回避時はゲスト受入を閉じられる。基本的な識別・再接続は別途確認する。処分や包括的制限の変更で過去レートを自動取消しない。

<a id="verification-030"></a>
## 組織・インスタンスの分離

組織内で管理者・ユーザーを共有し、配下インスタンスでモデレーター・問題・レート・待機列・部屋を分ける方向を計画へ反映する。

同組織内と別組織間の両方で、インスタンス別の認可を確認します。

受入の追加対象は、管理画面からのインスタンス追加（別DB/Auth構築・追加デプロイ不要）、同一アカウントでの複数インスタンス利用、インスタンスを跨ぐ権限・問題管理・レート・待機列・部屋の混入防止、対象インスタンスを示す画面導線、既存人物識別・履歴・結果の移行保持。

同組織内の共通ユーザーにはインスタンス間の外部参加許可を要求しないこと、別組織への参加は元・先インスタンス間の設定で制御すること、問題・結果共有は同組織内でも個別設定に従うことと、一括設定操作が選択対象以外・後から追加されたインスタンスへ波及しないことを追加受入とする。

機能ごとの実装と画面受入は[計画](plan.md)に従います。

<a id="verification-031"></a>
## 引継ぎ・退会・共有の受入

- 管理者引継ぎは後任承諾前に現管理者を失わず、承諾後に指定した権限状態になる。
- 完全削除は管理者のみが対象名を一致させてSubmitした場合に実行し、不一致・別対象・無権限では実行しない。具体的な消去範囲は実装前に確定する。
- 共有解除・取得エラーになった共有元の問題を新規出題に使わず、進行中の固定内容を変更しない。
- 短い読みが長い読みの先頭でも、登録済み正解へ最初に到達した時点で正解とする。登録外の共通接頭辞では終了せず、分岐した正解も受け付ける。
- 退会の通常非表示・相手結果と必要な調査記録保持は承認済み。退会者のアカウント利用拒否、通常プロフィールとランキングからの非表示、相手履歴の「退会ユーザー」表示、相手の勝敗・レート維持、運営の権限内閲覧を確認する。

  保持項目・期間は別途確定する。

## アカウント単位の同時参加

自動待機・部屋ロビー・回答者・出題専任の組合せで、同じアカウントの参加枠を最大2つに制限し、新参加の成立後に前の本人だけを離脱させることを確認します。別組織への参加は組織間連携段階の後続検証です。
複数タブ・同時要求・取消と再参加・通信の応答消失で旧参加を復活させません。閲覧だけでは開始済み試合を解除せず、自動待機は画面移動、部屋ロビーは別機能・一覧への移動で解除します。最後の接続切れで自動待機を除外し、別タブが接続中なら保持します。取消時点で開始済みなら試合と30秒の復帰猶予を維持します。

## 表示名・引継ぎ・移行

- 同一組織で表示名の重複と同時登録・変更競合を拒否し、別組織の同名は別人として扱う。名前変更の回数制限を設けず、現在プロフィール・ランキングだけが即時更新され、待機・対戦・過去結果と不変IDは変わらない。
- 管理者招待の7日間の期限、取消、承諾時の再認可、旧管理者の権限を残す／外す選択を検証する。全管理者のアカウント喪失時は、設置者のサーバー側復旧と監査を確認する。
- 移行時は新規受付停止・待機解除の後、対戦終了と結果保存を待つ。問題・戦績・レート・公開状態の保持を照合してから再開する。

## 審査なし方式への切替

審査中の新規投稿・改訂が、取下げ・再提出・個別承認なしで審査を通ることを確認します。使用停止・形式検証を維持し、未提出の下書きを公開せず、進行中の試合・過去結果を変更しません。

## 作問者資格

- 同じインスタンスの申請中は1件とし、他インスタンスの資格を投稿許可に使わない。
- 不承認理由と再申請可能日時を本人へ表示し、管理者設定の待機期間内は再申請を拒否、満了後は受け付ける。
- 資格管理担当だけが承認・不承認・直接付与・取消を操作でき、直接付与で申請中の申請も承認済みになる。
- 取消で審査中・差戻し中の審査を終了して下書きを残し、公開済み・使用停止中の状態を変えない。再付与で終了した審査を再開しない。
- 承認作問者限定方式では取消後の提出を拒否する。一般投稿方式では資格取消だけで投稿を禁止せず、個人の投稿制限を別途適用する。
