# ADR 0001：MVPの構成と信頼境界

日付：2026-09-07。状態：ユーザー提示企画で採用、実装未検証。CSSの選定のみ[ADR 0003](0003-tailwind-css.md)で更新。他の決定は継続。

## 背景

独立した運営主体を横断する早押し体験と結果共有を、成功・停止・復旧まで説明できる技術デモとして構築する。

## 決定

- インスタンスごとに管理者・DB・Auth・署名鍵を分離する。
- 当初企画のUIはReact/TypeScript/Panda CSS。CSSは[ADR 0003](0003-tailwind-css.md)でTailwind CSSへ変更済み。APIはHono on Workers、対戦は1ルーム1DO、永続DBとAuthはSupabaseとする。
- 開催元が唯一の裁定者で、参加者は開催元へWebSocket接続する。
- 手動承認peer間の独自HTTPS JSON v1を使用する。ActivityPub互換とはしない。
- ルール、問題、採点版、大会条件を固定し、改訂を過去試合へ遡及しない。
- DOで未保存結果を永続保持し、DBの結果とoutboxは同じTXで確定する。
- 配送は再送可能とし、重複排除と有効イベントからの順位再生成で収束させる。
- MVP完了に独立A/Bの参加・問題共有・結果共有・停止復旧を含める。

## 影響

連合先の停止から試合進行を分離できる。通信遅延差や悪意ある開催元の不正裁定はこの構成だけでは解消できず、認定開催元と除外の運用が必要になる。DOとDBは単一TXではないため、UIで保存中を扱う。クラウド非依存化にはDOの代替が必要。

## 初期に採用しない代替案

peer間合意による各buzzの裁定、共有DBによる疑似連合、任意コードのルール、AI採点、公開自動連合、世界共通レーティング、Docker/VPS移植はMVPの目的に対して範囲が大きいため後続検討とする。
