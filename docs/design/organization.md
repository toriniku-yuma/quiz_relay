# 組織・インスタンスの設計

[一覧](../README.md) ／ [組織仕様](../spec/organization.md)

**既存actorId・owner・結果原本を保持して、1組織内のインスタンスを分離します。**
基盤は実装済みです。運営機能全体・既存クラウド移行の受入は未完了です。

1つのWorker・Auth・Postgresを組織内で共用し、追加インスタンスへ問題・戦績・権限を自動コピーしません。
同組織の参加に外部参加許可を要求せず、問題・結果共有は個別に設定します。

## 既存の本人識別とデータを保持する

- 組織に変更不可の識別用値を持たせる。

  既存環境では移行前のGAME_OWNERをそのまま保存し、actorIdの計算を従来と同じ `contentHash({ home: identityNamespace, subject: verifiedSubject })` に保つ。

  新規構築では `urn:uuid:<組織ID>` を識別用値として保存する。表示名・URL・利用先インスタンスはこの計算に使わない。
- Auth subjectは必ず既存のサーバー側getUserで検証した値を使う。組織内アカウント表ではsubjectとactorIdをそれぞれ一意に保持し、初回ログインで対応を登録する。

  過去のactorIdを変更しないため、まだ新構成へログインしていない人の結果やランキングもそのまま残る。
- 既存環境の移行時は、最初のインスタンスが既存ownerをデータ参照用の値として引き継ぐ。インスタンスの内部IDとownerは一意対応させ、既存の問題・設定・結果・outboxのownerやpayloadを一括書換えしない。

  新規構築の最初のインスタンスと追加インスタンスには、`urn:uuid:<インスタンスID>` をownerとして発行する。
- results/read.tsは引き続き対象ownerとactorIdで取得できる。組織内で同一actorIdを使っても、owner条件を除いてレートを合算しない。

  アカウント行が未作成という理由で過去result_playersを除外しない。
- 移行前に複数owner・複数Auth基盤・異なる本人識別規則が見つかった場合、この単一旧環境の移行案を機械的に適用しない。対応を調査し、表示名やメール一致による統合を避ける。

## 追加する永続情報と認可

| 情報 | 最低限の役割・制約 |
| --- | --- |
| 組織 | 1配置の組織レコード、内部ID、表示名、変更不可のidentityNamespace、初期設定完了状態 |
| 組織アカウント | 検証済みAuth subject・actorIdの一意対応、組織共通の管理者権限。退会・処分の完成は運営機能 |
| インスタンス | 組織、内部ID、変更不可のデータowner、表示名、準備中（非公開・全体休止）／公開。アーカイブ等は運営機能 |
| インスタンス権限 | インスタンスとactorIdの組合せ、付与された既決パーミッション。Aの権限でBを管理できない |

認証→対象インスタンスの存在・組織の確認→公開状態または管理権限の確認→個別操作の認可、の順で処理する。対象はサーバーで解決し、ブラウザーがownerを直接指定して権限判定を省略するAPIにしない。

設定・問題の複合参照はownerが一致するDB制約を維持する。

Web管理には必要な表と操作だけを許可したDBロールを設計する。既存の管理用資格情報・migrationロール・service_roleをWorkerやブラウザーへ流用しない。

catalog_operatorsはCLI用のDBロール認可であり、Webモデレーターへそのまま渡さない。

## 初回管理者の設定

設置者確認は、初回管理者にするAuth subjectを設置者がサーバー設定へ指定する方式とする。subject自体は認証情報ではなく、それを知っているだけでは設定を完了できない。

1. 設置者が初回設定画面から既存のメール／Google認証でログインする。
2. 未設定時のみ、ログイン中の本人の識別子と、サーバー側にその識別子を指定する手順を表示する。
3. 設置者が配置環境の初回管理者設定へ指定する。アプリは指定されたsubjectと、検証済みログインのsubjectが一致するときだけ組織名等の確定を受け付ける。
4. 組織・初期管理者・最初のインスタンスを同一DBトランザクションで登録し、初回設定済み状態を確定する。並行した設定要求は1回だけ成功させる。
5. 完了後は初回設定経路から追加昇格・初期化できない。設定の除去や通常再起動でも初期設定を再開しない。応答消失時は設定済み状態を確認して管理画面へ進む。

設定値をAPIで公開する必要はなく、DB管理パスワード等を初回画面で入力させない。既存データの移行時にも、最初にアクセスした人や過去の参加者を自動的に管理者にしない。移行データと初回設定を結び付ける順序は移行リハーサルに含める。

## 同時参加は既存Matchmakerを組織単位に拡張する

参加枠は自動待機・部屋ロビー・回答者・出題専任・別組織の対戦で共通です。外部参加でも所属組織側の予約を保持し、外部開催先の参加予約と対応付けます。複数タブ・インスタンス・役割を使った二重参加を許可しません。閲覧・管理操作は参加枠を消費しません。

別のロック専用サービスは現在は追加しない。組織ごとに1つのMatchmakerを使い、既存のactor予約を共通化する。

各予約にはinstanceId・mode・roomId・世代を持たせ、相手を探す条件と人数・ルール・問題はインスタンス別に分離する。物理的な調整役の共有は、待機列やレートを混ぜる意味ではない。

- 参加要求時、対象インスタンスの認可と固定条件の取得を経て、保存済みactor予約を確認する。別のインスタンスへの参加中なら新しい予約を作らず、参加先へ戻れる案内を返す。
- 部屋予約RPCの前にactor・instance・mode・room・世代・復帰用情報を保存する。同じ要求の再試行では同じ部屋へ進み、RPC応答消失で別部屋を作らない。
- DB読込中や取消と新規参加の競合には、既存のadmissionId方式を対象インスタンスと結び付けて使う。古い応答で新しい予約を上書きしない。
- 復帰は保存済みの参加先へ戻す。画面切替・切断・一時停止だけで予約を解放しない。ログアウトによるトークン無効化も、進行中試合から自由に次試合へ乗り換える抜け道にしない。
- 待機取消は部屋側の取消成立を確認してから、同じ世代の予約だけを解除する。取消要求の遅延が次の予約を解除しないようにする。
- 部屋の終端状態が永続化されたことを確認したら参加枠を解放できる。結果DB保存の再試行はGameRoomに残し、参加枠解除で未保存結果を削除しない。レート表示は既存の保存確定状態に従う。
- 通信失敗や状態取得タイムアウトは、部屋が終了した証拠にしない。成否不明の予約は同じ世代・部屋で照合し、単なる時間切れで解除して遅延RPCを二重成立させない。
- GameRoomの予約・認証には対象instanceと世代の対応を保持する。旧世代を閉じる場合は遅延した予約を再成立させない確認が必要。具体的な保存形式とRPC契約を実装設計で定める。

GameRoom RPCを予約表の直列処理中に待つと、組織化すると遅い部屋が他インスタンスへ影響しうる。RPC待ちと保存処理の分離、限定した状態照合、世代照合をセットで設計する。

組織全体を直列化したまま規模無制限と扱わない。既存の部屋数等の制限も、組織全体へ無言で読み替えない。規模の確認は負荷試験で行い、必要になる前に新たな分散基盤を追加しない。

## API・画面の接続

- 共通認証の後に対象インスタンスを解決する処理を追加し、設定取得・参加・取消・復帰・結果取得・管理操作で共用する。ルート定義に業務処理を埋め込まず既存の責務分割を保つ。
- 対象インスタンスはURL等で明示する。ブラウザー全体の「現在選択中」変数だけで判断せず、複数タブのAでの操作がBへ送られないようにする。
- 準備中の参加権限を取り消したら未開始の待機を解除する。部屋の予約・接続・開始直前にもDBで本人と対象インスタンスの権限を確認し、変更通知の失敗は待機列の定期確認で再処理する。本人の取消と開始済み試合の復帰は継続できるが、新規参加・設定取得・履歴取得の認可は緩めない。
- 部屋トークンは部屋・本人・インスタンスに結び付ける。APIパス変更時はcookieのpath、取消時の削除、既存復帰導線も合わせて設計する。
- 組織基盤の画面は、初回設定、組織のインスタンス一覧・追加、インスタンス設定・公開開始、対象が明確な既存対戦と履歴への入口。正式な作問・審査画面は作問機能で追加する。

## 障害・競合を含む検証項目（未実施）

| ケース | 期待する結果 |
| --- | --- |
| 別アカウントが初回設定へアクセス | 設置者指定の本人でなければ管理者登録不可 |
| 初回設定を同時送信／保存後の応答消失 | 1組織・1回の初期設定になり、再送で余計な管理者を作らない |
| 組織名・インスタンス名を変更 | actorId・owner・過去履歴・レートが変わらない |
| A・Bへ同じactorが同時参加要求 | 片方だけ予約成立。再試行で参加先が入れ替わらない |
| 部屋予約成功後にRPC応答消失 | 同じ予約へ復旧し、二重参加しない |
| 取消と別インスタンス参加が競合 | 古い取消・取得応答が新しい世代を解除・上書きしない |
| 切断・DO再起動・画面切替 | 元の参加と期限を維持。対戦の復帰猶予を延長しない |
| 部屋の状態取得が失敗 | 終了扱いして別の対戦を開始しない。復旧後に照合できる |
| 終端後にDB保存が失敗 | 原本と再試行を保持し、参加枠の更新でも失わない |
| 準備中のインスタンスへURL／API直接アクセス | 一般利用者の対戦・作問を拒否。組織管理者・対象インスタンスの管理権限を持つモデレーターは通常対戦へ参加可。個別停止中も対象の管理権限者は参加可 |
| Aの管理権限でBのIDを送信 | 読取・更新・公開操作を拒否 |
| 旧データを移行、利用者が再ログイン | 問題・原本・outboxのハッシュ不変、過去履歴とレート一致 |
| 未ログインの旧利用者 | 過去結果・ランキング集計から消えない |

検証の実施状況は[実装・レビュー](../history/organization.md)を参照します。

## 非公開中の通常利用と開発検証

非公開中の管理権限者も通常の対戦API・裁定・結果保存を使います。公開状態によってレートや集計をテスト扱いへ変えません。個別機能の停止は公開状態とは別に検証し、どちらも組織管理者・対象インスタンスの管理権限を持つモデレーターには通常参加を許可します。専用テスト対戦・専用履歴は設けません。開発用の対戦検証は[検証項目](../development/testing.md#開発環境での対戦検証)に従い、一般ユーザー向けの機能と分離します。

## 既存環境の移行

1. 対象環境を指定し、スキーマ版・既存owner・Auth構成・データ件数・結果ハッシュ・利用者別レート・未保存結果・DO状態を調査する。現在のローカルとクラウドの差を確認する。
2. 復元可能なバックアップを準備し、隔離した検証環境で追加型の移行を試す。適用済み0000〜0010の再適用や初期seedの再投入はしない。
3. 組織・インスタンス・アカウントの対応を追加する。既存データを最初のインスタンスへ対応付ける。問題の出典や作問者が現行データで分からない場合は架空の投稿者を補わない。
4. 原本・outboxの件数とハッシュ、固定版参照、本人履歴、インスタンス別レートが移行前後で一致することを確認する。新しいアカウントと過去actorを別人として二重集計しない。
5. 切替時は新規受付を止め、待機を解除し、進行中の対戦と未保存結果の保存完了を待ってから移行する。対戦を強制終了しない。旧DOを新名前空間へ無条件に置き換えない。既存の問題・戦績・レート・公開状態を維持する。実行日時・実測停止時間は運用の実施記録に残す。
6. 復帰・認可・結果保存を確認して新規参加を再開する。失敗時は新規書込みを止めて調査し、新構成で受理した結果を捨てる単純なバックアップ巻戻しはしない。復旧手順はリハーサルで検証する。
