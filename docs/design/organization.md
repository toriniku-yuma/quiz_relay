# 組織・インスタンスの設計

[一覧](../README.md) ／ [組織仕様](../spec/organization.md)

**組織の識別名前空間とインスタンスの不変ownerで、1組織内のインスタンスを分離します。**
基盤は実装済みです。運営機能全体の受入は未完了です。

1つのWorker・Auth・D1を組織内で共用し、インスタンス間で問題・戦績・権限を自動コピーしません。
同組織の参加に外部参加許可を要求せず、問題共有はインスタンスごとに設定します。結果は参加記録に結び付けて所属元へ配送し、共有設定を設けません。

## 本人識別とデータの分離

- 組織に変更不可の識別用値 `identityNamespace` として `urn:uuid:<組織ID>` を保存する。actorIdは `contentHash({ home: identityNamespace, subject: verifiedSubject })` で求め、表示名・URL・利用先インスタンスはこの計算に使わない。
- subjectは必ずサーバー側でClerkのsession tokenを検証して得たClerkユーザーIDを使う。組織内アカウント表ではsubjectとactorIdをそれぞれ一意に保持し、初回ログインで対応を登録する。
- 各インスタンスには `urn:uuid:<インスタンスID>` をownerとして発行する。インスタンスの内部IDとownerは一意対応させ、問題・設定・結果・outboxはownerで分ける。
- Workerの環境変数に開催元ownerを持たない。対戦・結果・カタログの対象ownerは、認可したインスタンスから毎回解決する。インスタンスを持たない開発参加（`/local-game/`）だけは、`config/matchmaking*.json` のownerへ反映した出題設定を読む。
- results/read.tsは対象ownerとactorIdで取得する。組織内で同一actorIdを使っても、owner条件を除いてレートを合算しない。

## 追加する永続情報と認可

| 情報 | 最低限の役割・制約 |
| --- | --- |
| 組織 | 1配置の組織レコード、内部ID、表示名、変更不可のidentityNamespace、初期設定完了状態 |
| 組織アカウント | 検証済みAuth subject・actorIdの一意対応、組織共通の管理者権限。退会・処分の完成は運営機能 |
| インスタンス | 組織、内部ID、変更不可のデータowner、表示名、準備中（非公開・全体休止）／公開。アーカイブ等は運営機能 |
| インスタンス権限 | インスタンスとactorIdの組合せ、付与された既決パーミッション。Aの権限でBを管理できない |
| 利用者のお気に入り | `account_instance_selections` のactorId・instanceIdの組を主キーとする。登録は本人の明示操作だけ。権限・外部参加許可を持たせない |

認証→対象インスタンスの存在・組織の確認→公開状態または管理権限の確認→個別操作の認可、の順で処理する。対象はサーバーで解決し、ブラウザーがownerを直接指定して権限判定を省略するAPIにしない。

設定・問題の複合参照はownerが一致するDB制約を維持する。

D1にはDBロールがないため、Web管理で扱える表と操作はWorkerの認可で限定する。DBをブラウザーへ公開しない。

設置者用CLIは `CATALOG_SUBJECT` に指定した組織管理者と、引数で指定した対象インスタンスのownerを照合して認可する。Webモデレーターの権限とは結び付けない。

## 初回管理者の設定

設置者確認は、初回管理者にするAuth subjectを設置者がサーバー設定へ指定する方式とする。subject自体は認証情報ではなく、それを知っているだけでは設定を完了できない。

1. 設置者が初回設定画面からGoogle認証でログインする。
2. 未設定時のみ、ログイン中の本人の識別子と、サーバー側にその識別子を指定する手順を表示する。
3. 設置者が配置環境の初回管理者設定へ指定する。アプリは指定されたsubjectと、検証済みログインのsubjectが一致するときだけ組織名等の確定を受け付ける。
4. 組織・初期管理者・最初のインスタンスを同一DBトランザクションで登録し、初回設定済み状態を確定する。並行した設定要求は1回だけ成功させる。
5. 完了後は初回設定経路から追加昇格・初期化できない。設定の除去や通常再起動でも初期設定を再開しない。応答消失時は設定済み状態を確認して管理画面へ進む。

設定値をAPIで公開する必要はなく、DB管理パスワード等を初回画面で入力させない。最初にアクセスした人を自動的に管理者にしない。

## 同時参加は組織単位のMatchmakerで制御する

参加枠は自動待機・部屋ロビー・回答者・出題専任・別組織の対戦で共通です。外部参加でも所属組織側の予約を保持し、外部開催先の参加予約と対応付けます。複数タブ・インスタンス・役割を使った二重参加を許可しません。閲覧・管理操作は参加枠を消費しません。

別のロック専用サービスは現在は追加しない。組織ごとに1つのMatchmakerを使い、actor予約を組織内で共通にする。

各予約にはinstanceId・mode・roomId・世代を持たせ、相手を探す条件と人数・ルール・問題はインスタンス別に分離する。物理的な調整役の共有は、待機列やレートを混ぜる意味ではない。

- 参加要求時、対象インスタンスの認可と固定条件の取得を経て、保存済みactor予約を確認する。別のインスタンスへの参加中なら新しい予約を作らず、参加先へ戻れる案内を返す。
- 部屋予約RPCの前にactor・instance・mode・room・世代・復帰用情報を保存する。同じ要求の再試行では同じ部屋へ進み、RPC応答消失で別部屋を作らない。
- DB読込中や取消と新規参加の競合には、admissionId方式を対象インスタンスと結び付けて使う。古い応答で新しい予約を上書きしない。
- 復帰は保存済みの参加先へ戻す。画面切替・切断・一時停止だけで予約を解放しない。ログアウトによるトークン無効化も、進行中試合から自由に次試合へ乗り換える抜け道にしない。
- 待機取消は部屋側の取消成立を確認してから、同じ世代の予約だけを解除する。取消要求の遅延が次の予約を解除しないようにする。
- 部屋の終端状態が永続化されたことを確認したら参加枠を解放できる。結果DB保存の再試行はGameRoomに残し、参加枠解除で未保存結果を削除しない。レート表示は既存の保存確定状態に従う。
- 通信失敗や状態取得タイムアウトは、部屋が終了した証拠にしない。成否不明の予約は同じ世代・部屋で照合し、単なる時間切れで解除して遅延RPCを二重成立させない。
- GameRoomの予約・認証には対象instanceと世代の対応を保持する。旧世代を閉じる場合は遅延した予約を再成立させない確認が必要。具体的な保存形式とRPC契約を実装設計で定める。

GameRoom RPCを予約表の直列処理中に待つと、組織化すると遅い部屋が他インスタンスへ影響しうる。RPC待ちと保存処理の分離、限定した状態照合、世代照合をセットで設計する。

組織全体を直列化したまま規模無制限と扱わない。既存の部屋数等の制限も、組織全体へ無言で読み替えない。規模の確認は負荷試験で行い、必要になる前に新たな分散基盤を追加しない。

## API・画面の接続

`POST /api/organization/settings` は組織管理者だけが使い、`{ name, expectedName }` で組織名を変更します。空白・80文字超過を拒否し、保存済みの名前が `expectedName` と違う場合は409を返します。同じ名前への再送は監査記録を追加しません。組織ID・本人識別のnamespace・インスタンスowner・アカウント・戦績は変更せず、連携メタデータのrevisionだけ更新します。

組織設定には名前変更とインスタンス一覧・作成を置き、個別の設定は各インスタンスへリンクします。相手組織の承認・ブロック・対戦種別の許可は組織管理の連携画面、問題共有の設定と結果配送の状況は個別インスタンスの「問題共有・結果配送」で扱います。ユーザー管理は組織管理に置き、管理者は組織全体を一覧できます。処分・権限・通報のポップアップから対象インスタンスを選び、切替前の入力や遅延応答を別の対象へ引き継ぎません。担当モデレーターは付与済みインスタンスだけを扱い、組織全体のBANは管理者に限定します。

- 共通認証の後に対象インスタンスを解決し、設定取得・参加・取消・復帰・結果取得・管理操作で共用する。対象インスタンスを解決できなければ処理を続けない。ルート定義に業務処理を埋め込まない。
- 対象インスタンスはURL等で明示する。ブラウザー全体の「現在選択中」変数だけで判断せず、複数タブのAでの操作がBへ送られないようにする。
- ランク・カジュアルの設定と取得エラーは閲覧先IDと一緒に保持し、その閲覧先の応答だけを表示する。参加・復帰・取消のエラーとは分け、設定取得の成功で応答不明の参加状態を消さない。結果リンクも共通部品で閲覧先IDと照合し、表示の切替で対戦コンポーネントや接続を作り直さない。
- 準備中の参加権限を取り消したら未開始の待機を解除する。部屋の予約・接続・開始直前にもDBで本人と対象インスタンスの権限を確認し、変更通知の失敗は待機列の定期確認で再処理する。本人の取消と開始済み試合の復帰は継続できるが、新規参加・設定取得・履歴取得の認可は緩めない。
- 部屋トークンは部屋・本人・インスタンスに結び付ける。APIパス変更時はcookieのpath、取消時の削除、既存復帰導線も合わせて設計する。
- 組織基盤の画面は、初回設定、利用可能なインスタンス一覧と本人の候補追加・解除、管理者の全件管理・作成、インスタンス設定・公開開始、対象が明確な既存対戦と履歴への入口。正式な作問・審査画面は作問機能で追加する。

組織情報APIの `instances` は発見・直接URLの解決・全件管理に使い、候補登録で絞りません。別項目 `addedInstanceIds` で認証本人の登録IDを返し、切替メニューはそのIDと現在利用可能な一覧の共通部分だけを表示します。一覧は登録IDから利用不可の解除用行も表示し、`instances` に含まれない先の名前や管理情報を追加取得しません。初期候補は空で、公開先を一括登録しません。

同APIの `sanctions` は認証本人の組織内の有効な処分だけを返し、他人・解除済み・期限切れの処分を含めません。既存の処分判定と期限更新hookを使い、一覧のランク・カジュアル・部屋の入口と部屋作成の入口を利用できる本人にだけ表示します。準備中・個別停止の対象管理権限による例外は既存仕様に従い、処分とカジュアル無効設定には例外を設けません。部屋はカジュアルの有効設定と独立し、部屋作成制限は入室の入口を隠しません。この表示判定は新規参加の案内だけに使い、既存接続の保持・復帰とサーバーの認可は変更しません。

`POST /api/organization/instances/selection` は `{ id, added }` を受け、認証済みsubjectから本人を解決します。追加時は既存の対象・公開状態・管理権限を確認し、解除時は利用不可になった先でも本人の登録を解除できます。IDごとのinsert／deleteを再送可能にし、別端末で異なる候補を変更しても全一覧の上書きは起こしません。閲覧先・参加先・管理権限を変更せず、Matchmakerへ操作を送りません。別端末はログイン・再読込・一覧の再試行で最新登録を読み込みます。

保存はWorkerのAPIだけが行い、ブラウザーへDBを公開しません。本人の退会と候補変更はD1のrevision照合付きbatchで順序を確定し、退会時・削除記録の復元適用時に登録を消します。インスタンス完全削除時は外部キーのcascadeで該当登録だけを消します。`account_instance_selections` は自組織のインスタンス専用で、外部組織の登録は別の表で扱います。

外部のお気に入りは[組織間連携の仕様](../spec/federation.md#外部インスタンスをお気に入りに追加する)に従い、`quiz_federation_favorites` へactorId・組織origin・instanceIdの組で保存します。同名・同じinstanceIdでも別組織の対象を混同しません。本人の登録は所属組織に保存し、接続先の承認・参加許可と別に扱います。ローカルの登録表へ外部IDを挿入したり、お気に入り追加のために管理用インスタンスを作成したりしません。

外部一覧の取得は承認済みpeerの署名付きメタデータに限定し、既存の送信先制限と鍵検証を維持します。利用者の操作で未知の接続先を承認したり、任意URLの取得を許可したりしません。お気に入り経由の参加も両側の参加許可と本人認証を確認します。

## 障害・競合を含む検証項目（未実施）

| ケース | 期待する結果 |
| --- | --- |
| 別アカウントが初回設定へアクセス | 設置者指定の本人でなければ管理者登録不可 |
| 初回設定を同時送信／保存後の応答消失 | 1組織・1回の初期設定になり、再送で余計な管理者を作らない |
| 組織名・インスタンス名を変更 | actorId・owner・過去履歴・レートが変わらない |
| A・Bへ同じactorが同時参加要求 | 片方だけ予約成立。再試行で参加先が入れ替わらない |
| 部屋予約成功後にRPC応答消失 | 同じ予約へ復旧し、二重参加しない |
| 取消と別インスタンス参加が競合 | 古い取消・取得応答が新しい世代を解除・上書きしない |
| 切断・DO再起動・画面切替 | 元の参加と期限を維持。対戦の復帰猶予を延長しない |
| 部屋の状態取得が失敗 | 終了扱いして別の対戦を開始しない。復旧後に照合できる |
| 終端後にDB保存が失敗 | 原本と再試行を保持し、参加枠の更新でも失わない |
| 準備中のインスタンスへURL／API直接アクセス | 一般利用者の対戦・作問を拒否。組織管理者・対象インスタンスの管理権限を持つモデレーターは通常対戦へ参加可。個別停止中も対象の管理権限者は参加可 |
| Aの管理権限でBのIDを送信 | 読取・更新・公開操作を拒否 |

検証の実施状況は[実装・レビュー](../history/organization.md)を参照します。

## 非公開中の通常利用と開発検証

非公開中の管理権限者も通常の対戦API・裁定・結果保存を使います。公開状態によってレートや集計をテスト扱いへ変えません。個別機能の停止は公開状態とは別に検証し、どちらも組織管理者・対象インスタンスの管理権限を持つモデレーターには通常参加を許可します。専用テスト対戦・専用履歴は設けません。開発用の対戦検証は[検証項目](../development/testing.md#開発環境での対戦検証)に従い、一般ユーザー向けの機能と分離します。

## 退会・再登録の実装設計

退会の成立、認証情報の削除、過去名の消去は別の進捗として記録します。画面上の匿名表示だけで物理削除完了と扱いません。

- 旧アカウントは退会済みの記録として保持し、同じAuth subjectの通常API利用を拒否します。現在のactorIdはsubjectから生成するため、アカウント行の削除・再生成では旧投稿や戦績につながってしまいます。再登録は新しいAuth subjectから作り、メール・Google属性一致で旧actorへ統合しません。
- Matchmakerに操作ID付きの受付停止を永続化してから参加状態を照合します。参加受付の最初と予約確定時の両方で停止を確認し、古いadmissionIdを無効化します。待機・進行中・状態不明なら退会は成立させず、同じ操作IDの停止だけを解除します。単なる「状態取得→DB更新」では参加との競合を防げません。
- 参加なしを確定した後、最後の管理者を残す条件・退会記録・認証削除ジョブを同一DB transactionで保存します。DB応答消失時は記録を照合し、成立済みの受付停止を解除しません。退会後は名前をNULLにして重複制約上の名前を解放し、既存セッションも無効化します。
- 認証削除は専用サービスに分離します。通常Workerはservice bindingへ退会操作IDだけを渡し、専用サービスがDBの成立済みジョブから対象subjectを得て、そのClerkユーザーを削除します。任意subjectの削除を受け付けず、ClerkユーザーIDの形式でないsubjectは削除完了にしません。通常Workerは本人確認のためClerkのsecret keyを持ちますが、ユーザー削除を呼びません。ブラウザーへAuth管理キーを渡しません。即時試行の失敗・応答消失を同じジョブで再試行し、完了後に再登録可能を表示します。自動処理と復旧CLIは同じ処理を使い、本番Cron・デプロイの適用は別途扱います。
- 即時の読取では退会者をランキングから除外し、参加名・作問者名を「退会ユーザー」にします。名前一致ではなくactorIdと投稿IDで対象を判断します。問題本文、相手の勝敗・レートは変更しません。
- 30日以内の消去では結果JSON・参加者表・outbox・作問カタログ・運営履歴・DO保存状態に残る旧名を対象にします。通常writerの不変制約を解除せず、対象と変更可能な名前の項目を限定した処理を設けます。原本hashと再送照合は同じ匿名化形式へ統一し、退会後に届く保存再試行でも旧名を復活させません。試合終了と結果DB保存完了は別なので、未保存結果を捨てて解決しません。
- バックアップ復元時にも退会・消去記録を再適用します。消去対象の調査と完了記録を含めて検証し、未実装の外部連携への匿名化通知を実施済みと扱いません。

## ユーザー管理・通報の永続化

user_reportsは対象・通報者・開催インスタンス・結果原本参照・理由を保存します。sanction_appealsは本人と処分版に結び付けます。元の理由と対応済みの判断は変更・削除を禁止し、既読だけを別に更新します。moderation_requestsは操作ID・本人・要求ハッシュ・内容を追記専用で保存し、応答消失後の同一再送を確認します。administrator_transfersは依頼元・引継先・依頼元の権限保持・期限・状態を保存します。承諾と権限変更は同一transactionです。

処分・権限変更・引き継ぎはD1のrevision照合付きbatchで保存し、競合時は読取りと認可の確認からやり直します。結果readerには組織の書込権限を追加せず、組織DBで解決したBAN対象を結果の集計前へ渡します。通報対象の試合は同一開催元の不変な結果原本で本人・相手の参加を照合します。

DOのanswerStatsは試合の作成時から保存します。REVEALING中だけ累積する時計を使い、解答・判定・再接続待ちは進めません。結果原本へコピーした後は書き換えません。調査の平均は試合平均の単純平均ではなく、記録された解答ごとの早押し時間から求めます。
