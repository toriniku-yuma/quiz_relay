# 退会・削除・保存期限の運用

[一覧](../README.md) ／ [運営仕様](../spec/organization.md) ／ [DB管理](database.md)

**アプリの利用停止と認証・保存データの消去を分け、非公開Workerと定期処理で再試行します。**
ローカルは通常アプリと同じD1・DOへ接続します。クラウドはmigration・秘密・bindingを設定し、対象とバックアップを確認して配置します。コードの保存だけでは定期処理は動きません。

## 専用Workerの設定

`wrangler.erasure.jsonc` は公開URL・公開ルートを持ちません。

| 設定 | 用途 |
| --- | --- |
| `GAME_D1` | 通常Workerと同じD1 ID |
| `AUTH_PROVIDER=clerk`・`CLERK_SECRET_KEY`・`CLERK_PUBLISHABLE_KEY` | 通常アプリと同じClerkアプリの本人削除。JWT公開鍵は任意 |
| `GAME_ROOM`・`MATCHMAKER` | 通常アプリの既存DO。`script_name` を設置先と一致させる |
| `CLOUDFLARE_ACCOUNT_ID`・`GAME_ROOM_NAMESPACE_ID` | 既存部屋の全件照合先 |
| `DURABLE_OBJECTS_READ_TOKEN` | 対象DOの一覧を読む権限 |

通常Workerの `ACCOUNT_ERASURE` service bindingで呼びます。専用Workerを先に配置し、通常Workerの毎分Cronを有効にします。専用Worker自身にはCronを重複設定しません。bindingがない場合は退会・完全削除を受け付けません。

通常Workerの定期処理は、認証削除・匿名化・インスタンス削除・結果の匿名化を各少数件に分け、保持期限処理・部屋照合・問題振り返り消去を非公開POSTで順に呼びます。進捗と再試行予定はD1へ保存します。一つの失敗で残りの処理を止めず、最後に実行失敗を報告します。認証削除の失敗は1分から最大1時間へ間隔を延ばします。

非公開の `/status` へPOSTすると、認証削除・匿名化・完全削除の未完了件数、30日期限超過、最古の未完了退会日時、未照合インスタンス件数を返します。名前・メール・本人IDは返しません。30日の個人情報削除期限に間に合わない障害は運営が解消します。

`/maintenance` は既知の処理名だけを受け付けます。任意SQLや任意URLは渡せません。正常応答でも未完了なら次の定期実行で続行します。完全削除は全室の安全確認が終わってから受け付けます。進行中試合・未保存結果がある確認要求は取り消し、自動削除を予約しません。

## ローカル開発環境

1. [D1のmigrationとバックアップ](database.md)を準備します。
2. 初回だけ `pnpm maintenance:local setup` を実行します。通常アプリの `.dev.vars` と同じClerkキーから、Git対象外の `.env.erasure-local` を作ります。既存ファイルを上書きしません。
3. `pnpm dev` を再起動します。Viteが同じD1・既存DOへ専用Workerを接続します。この秘密ファイルは本番ビルドでは読みません。
4. CLIの照合・状態確認・保守の前には `pnpm dev` を止め、保存データをバックアップします。CLIは通常アプリと同じDO namespaceをローカルの1つのWorkerに接続し、別サーバーの登録先へ依存しません。`pnpm maintenance:local status` で未処理を確認します。`pnpm maintenance:local maintenance` は実際の退会・消去を実行するため、対象を確認して使用します。
5. 既存インスタンスの照合は次の手順に従い、`pnpm maintenance:local inventory` を実行します。終了後は `pnpm dev` を再起動します。

Clerkの接続先が通常アプリと異なる設定は拒否します。ローカルCronは起動だけでは実行されず、開発中はCLIで続行します。クラウドDB・Cron・デプロイは変更しません。`.wrangler` の保存データはViteの監視から除外します。

## 既存部屋の照合

新規部屋は作成前に実DO IDをD1へ登録します。既存インスタンスは休眠部屋も含む全件照合が終わるまで退会・完全削除を受け付けません。

1. 対象を準備中またはアーカイブにし、書込みを止めてDB・DOをバックアップします。
2. 非公開の `/inventory` をPOSTします。クラウドはDO一覧API、ローカルはGameRoomの保存ディレクトリを列挙し、部屋自身のownerと照合します。
3. 1回で最大25部屋を照合します。`ready: false` の間は再実行し、失敗時は保存済み進捗から再開します。CLIは完了まで続けます。
4. `status` で未照合が0になったことを確認して公開状態を戻します。

保存ディレクトリの欠落、不明なファイル、元DBのないWALは完了扱いにしません。`room_inventory_complete` を手でtrueにしません。ローカルとクラウドのDO一覧を流用しません。

## 消去記録とバックアップ復元

退会・インスタンス完全削除の最新記録は、通常バックアップと独立して保管します。古いバックアップだけの復元では、その後の退会・削除を認識できません。

1. `node scripts/privacy-journal.ts export 保存先.json` でローカルD1から記録を出力します。既存ファイルを上書きしません。
2. Auth subjectを含むため、Git・公開ストレージ・通常ログを避け、アクセス制限した独立保管先へ保存します。外部への自動転送はしません。
3. 復元では一般アクセス・書込みを止め、DBとDOを復元し、全migrationを適用します。
4. `node scripts/privacy-journal.ts restore 保存先.json --apply` で最新記録を適用します。組織と本人namespaceが違う記録を拒否し、インスタンスを準備中にして退会者の権限解除・消去を再予約します。
5. 部屋照合を完了し、maintenanceを未完了がなくなるまで実行します。削除済みの復元部屋・DBも再消去します。退会者の認証・旧名と、削除済みインスタンスが残っていないことを確認してから公開します。

このCLIはローカルD1用です。クラウドではアクセスを止めた専用復旧経路を用意し、同じ照合・認可を適用します。最新記録を確保できない場合や照合失敗時は、復元データを公開しません。

## 保持するデータ

保存期間は[運営仕様](../spec/organization.md#通知履歴の保存期間)に従います。振り返りの期限消去でも勝敗・確定レートを変えません。部屋内コピーは結果保存確認後にだけ消去し、未保存結果は再送できるよう保持します。
退会では本人IDを再利用せず、投稿問題と相手の結果を匿名化して保持します。完全削除は受付記録に一致するインスタンスだけを消し、共通アカウント・他インスタンスを残します。

## 連携の定期処理と障害復旧

通常Workerの毎分Cronから同じ非公開Workerを呼びます。自側のFEDERATION_ORIGIN・SIGNING_KID・SIGNING_PRIVATE_KEYを両Workerに設定し、鍵をDBや画面へ保存しません。

| 処理 | 1回の上限・復旧方法 |
| --- | --- |
| 相手の公開情報 | 4ジョブ。100インスタンスずつ固定snapshotを取得し、期限と次cursorを保存 |
| 問題共有 | 2取り込み、各25問。途中のsnapshotを出題へ使わず、整合確認後に反映 |
| 結果配送 | 2宛先。署名原本とeventIdを固定し、受領後も本人履歴への適用を区別 |
| 匿名化・停止通知 | 2配送・1受信適用。tombstoneを先に保存し、遅延参加・復元で復活させない |
| 外部参加の期限 | 2閉鎖。未確認の枠解放を先に再試行し、期限切れセッションを100件まで消去 |
| nonce・共有本文の期限 | nonce100件、共有本文25件。操作の閉鎖原本・除外指定・過去結果を残す |

通信失敗は指数バックオフ、429はRetry-Afterを守ります。管理画面の「サーバー間の連携」「共有問題」で最終成功・エラー・未配送・隔離を確認し、同じ操作を再試行します。承認を止めた相手へは新規参加を認めず、配送原本を捨てずに保留します。別hashの原本を手で上書きしません。

共有問題は取得成功から90秒以内だけ新規試合へ使い、取得失敗を検知した時点で閉じます。毎分更新の時刻差を吸収する有効期限であり、停止を無視する猶予ではありません。30日後の未使用本文消去でも系列ID・除外・出典を保持し、進行中・過去結果の保存期限を別に適用します。
