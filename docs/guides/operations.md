# 退会・削除・保存期限の運用

[一覧](../README.md) ／ [運営仕様](../spec/organization.md) ／ [DB管理](database.md)

退会・完全削除はD1で受付条件を確認し、非公開Workerでその場の消去を進めます。失敗と未完了分はD1へ保存し、毎時Cronで再試行します。

## 専用Workerの設定

`wrangler.erasure.jsonc`は公開URL・公開ルートを持ちません。

| 設定 | 用途 |
| --- | --- |
| `GAME_D1` | 通常Workerと同じD1 |
| `CLERK_SECRET_KEY` | 通常アプリと同じClerkアプリの本人削除 |
| `GAME_ROOM`・`MATCHMAKER` | 開催元の期限切れ予約の取消 |
| `ACCOUNT_ERASURE` | 専用Worker自身へのservice binding。継続処理に使用 |
| `FEDERATION_LIMITER` | 通常Workerと同じnamespaceの連携制限。相手ごとに毎分600回 |
| `FEDERATION_ORIGIN`・`SIGNING_KID`・`SIGNING_PRIVATE_KEY` | 自側の連携署名 |

通常Workerにも専用Workerへの`ACCOUNT_ERASURE`を設定します。設定がない場合は退会・完全削除を受け付けません。DO一覧APIの資格情報は不要です。

## 実行と受付条件

退会はD1に本人の進行中試合がある間は拒否します。別サーバーでの参加は数えません。完全削除は、対象インスタンスの進行中・保存待ち試合がある間は拒否します。受付後は新しい試合の開始を拒否し、消去を進めます。

認証削除・匿名化・完全削除・制御イベント・結果配送は発生時に実行します。1バッチで終わらない消去・取り込みは自己service bindingで最大32回まで続け、残件は毎時処理へ引き継ぎます。認証削除や通信に失敗した場合は再試行予定を保存し、429のRetry-Afterより前に再送しません。

非公開の`/maintenance`は既知の処理名だけを受け付けます。`/status`は認証削除・匿名化・完全削除の未完了件数、30日期限超過、最古の未完了退会日時を返します。名前・メール・本人IDは返しません。

## ローカル開発環境

1. D1とDOをバックアップし、現在のスキーマを準備します。
2. 初回だけ`pnpm maintenance:local setup`を実行し、通常アプリと同じClerkキーから`.env.erasure-local`を作ります。既存ファイルを上書きしません。
3. `pnpm dev`を再起動します。Viteが同じD1とDOへ専用Workerを接続します。秘密ファイルは本番ビルドで読みません。
4. CLIを使う前は開発サーバーを止めます。`pnpm maintenance:local status`で未処理を確認し、`pnpm maintenance:local maintenance`で毎時・日次の処理を実行します。

Clerkの接続先が通常アプリと違う設定は拒否します。CLIは実際の認証削除・消去を実行します。ローカルCronは起動だけでは実行されません。

## 消去記録とバックアップ復元

退会・完全削除の最新記録は通常バックアップと独立して保管します。

1. `node scripts/privacy-journal.ts export 保存先.json`でローカルD1の記録を出力します。
2. Auth subjectを含むため、Git・公開ストレージ・通常ログへ置かず、アクセス制限した場所で保管します。
3. 復元時は一般アクセスを止め、同じ版のD1・進行中DO・設定を復元します。確定済みDOは復元不要です。
4. `node scripts/privacy-journal.ts restore 保存先.json --apply`で最新記録を適用し、退会者の権限と削除対象を再確認します。
5. 未完了の消去を完了させ、退会者の認証・旧名・削除済みインスタンスが残らないことを確認して公開します。

旧形式からの移行には使いません。今回の検証環境はバックアップ後にD1・DOを再構築し、初期migrationと設定を投入します。復旧が必要なら、再構築前のアプリ版・DB・設定を一組で戻します。

## 保持するデータ

保存期間は[運営仕様](../spec/organization.md#通知履歴の保存期間)に従います。振り返りと名前の消去で勝敗・確定レートを変えません。結果確定と終了通知が終わった試合DOはその場で削除します。未確定の結果はDOに残し、保存を再試行します。

部屋を閉じるとD1のメンバー・秘密値・持込原本を消し、親DOを削除します。本人の保存問題セットと確定試合の振り返りはそれぞれの保存条件に従います。

## 連携の定期処理と障害復旧

通常WorkerのCronはUTCで`0 * * * *`と`0 19 * * *`の2本です。消去WorkerにはCronを設定しません。

再試行の期限は、Cronの元の予定時刻ではなく実際の実行時刻で判定します。同じCronイベントが再度配信されることを復旧条件にせず、保存済みの失敗ジョブを次の毎時処理で回収します。元と同じ予定時刻の再実行が届いた場合も、現在時刻で期限を判定します。`maintenance_task`ログの`runId`と`taskIndex`で開始・終了を対応付け、`frequency`で毎時・日次を区別します。終了時の`outcome`は`ok`（成功）、`pending`（残件あり）、`failed`（失敗）です。終了ログだけで成功と判断せず、失敗対象の最終成功時刻・エラー解除・残件の解消を確認します。

| 周期 | 処理 |
| --- | --- |
| 毎時 | 認証削除・結果配送・制御イベント・継続処理の残件、共有元・問題取り込みの失敗と未完了分、期限切れ未閉鎖予約、メタデータの同期 |
| 日次 | 共有元・問題取り込みの同期、結果と記録の保存期限、nonce・セッションの期限切れ、共有本文の30日処理、難易度集計 |

共有元・問題取り込みの通常同期は日次、メタデータは毎時に、期限が来た対象を選び、対象ごとに非公開Workerへ直列に依頼します。日次処理は対象の実行予定をD1に保存してから依頼し、途中停止・通信失敗・バッチ上限の残件は毎時に再開します。通信失敗では取得済みのsnapshotとcursorを保ち、相手のsnapshotが変わった場合だけ先頭から取得します。対象数だけで次の時間帯へ繰り越さず、失敗した対象があっても残りを処理します。結果配送・制御配送・認証・退会・削除の最初の選択は各2件です。継続対象は1要求32バッチまで進めます。予約取消は1バッチ2件、セッション消去は各100件です。

公開情報は毎時同期し、有効期限は成功から62分です。共有問題は日次（UTC 19時、日本時間4時）に同期し、有効期限は成功から24時間2分です。急ぐ場合は管理画面から手動同期できます。取得失敗時は新規利用を止め、進行中の固定内容は維持します。管理画面で最終成功・エラー・未配送・隔離を確認します。別hashの原本を手で上書きしません。
