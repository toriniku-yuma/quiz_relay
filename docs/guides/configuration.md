# 人数・ルールの変更

[ドキュメント一覧](../README.md)

JSONを編集し、設定反映CLIで新しい固定版を作ります。開始済みの試合は変えません。

以下は固定版を登録するCLIの設定手順です。現在のランク出題は[対戦仕様](../spec/gameplay.md)に従い、投稿方式・カテゴリ割合・難易度・通報しきい値はインスタンスの管理画面で設定します。CLIによる手動セット参照・初期問題の登録は開発・初期構築用に維持します。

ランクマッチとカジュアルマッチの人数はインスタンス管理の「対戦の参加設定」でそれぞれ2〜4人に変更できます。保存は新規待機へ適用され、変更前の待機は以前の人数を保持するため、取消・再参加してください。
ルール・使用する問題セットやCLIによる人数設定はJSONで指定し、コマンドでDBへ反映します。通常の設定変更でTypeScript・SQL・大会版番号を編集する必要はありません。

初期値は4人、現在のローカル検証は2人を維持している。

<a id="configuration-002"></a>
## 設定ファイルの使い分け

| ファイル | 内容 | 反映方法 |
| --- | --- | --- |
| `config/matchmaking.json` | 標準の人数・ルール・DB問題セット参照。初期4人 | `default` プロファイルへ反映 |
| `config/matchmaking.local.json` | ローカル検証用の同じ項目。現在2人 | `local` プロファイルへ反映 |
| `config/runtime.json` | WebSocket監視・再接続、待機・予約・セッション期限、ルーム数・接続数・操作回数・イベント保持の運用値 | 開発サーバー再起動。本番ビルドは再ビルド・配置 |
| `wrangler.jsonc` / `.dev.vars` | 参照する `GAME_CONFIG_PROFILE`、binding・環境別接続 | 環境に応じて再起動・配置 |
| `.dev.vars` | Clerk・初回管理者 `INITIAL_ADMIN_SUBJECT`・ローカルCLIの管理者 `CATALOG_SUBJECT`。Git管理外 | 環境設定 |

秘密はconfig配下へ入れない。問題本文・正解も含めず、既存DBの問題セットID・版を参照する。初期投入問題の `seeds/mock-hiragana.json` は別用途で、アプリへ同梱しない。

<a id="configuration-003"></a>
## 人数を変更する例

ローカルなら `config/matchmaking.local.json` の `playersPerMatch` を2〜4の整数へ変更し、次を実行する。

```powershell
pnpm config:apply:local
```

これで新規マッチングへ反映される。既に参加中なら、待機を取り消して参加し直す。進行中の試合はそのまま完了する。4人へ戻す場合も同じJSONの値を4へ変更して同じコマンドを使う。

`pnpm config:apply:local` はファイル名・プロファイル・`--apply` を指定済みの用途別コマンドで、実際にDBへ反映する。標準設定は汎用コマンドで次のように反映する。

```powershell
pnpm config:apply config/matchmaking.json default --apply
```

プレビューは `pnpm config:apply config/matchmaking.local.json local` を使う。JSON検証と設定内容のJSON表示だけで、ネットワークアクセス・DB変更はしない。

別ファイル・別プロファイルには汎用の `pnpm config:apply <config.json> <profile> [--apply]` を使う。DB内の問題との整合性検証は `--apply` 時に行う。

CLIは通常開発環境と同じローカルD1へDrizzleで接続します。`.dev.vars` の `CATALOG_SUBJECT` が設定JSONのownerの組織管理者であることを確認し、未設定なら `CATALOG_SUBJECT_REQUIRED` で止まります。

この環境では登録済み。別プロジェクトの接続・権限は[DB管理](database.md)を参照。成功時はプロファイル・大会ID・版・人数だけを表示する。

JSONを保存しただけでは稼働中DBへ反映されない。DB反映後は、既に同じプロファイルを参照しているアプリの再起動・デプロイは不要。

プロファイルは環境の参照先名で、現在はローカル `.dev.vars` が `local`、Wranglerの既定が `default`。

<a id="configuration-004"></a>
## 人数以外の項目

| JSON項目 | 意味 | 現行初期値・許容範囲 |
| --- | --- | --- |
| `playersPerMatch` | 接続がそろうと開始する人数 | 4人（ローカル2人）、2〜4 |
| `rules.correctAnswersToWin` | 勝利する正解数 | 7、1〜100 |
| `rules.mistakesToDisqualify` | 失格になるお手つき数 | 3、1〜100 |
| `rules.choiceCount` | 文字パネルの候補数 | 4固定。その他の値は入力検証で拒否する |
| `rules.revealIntervalMs` | 本文1書記素の表示間隔 | 100、1〜10000ms |
| `rules.characterAnswerTimeMs` | 1文字の解答期限 | 3000、1〜60000ms |
| `rules.judgedDisplayMs` | 判定の表示時間 | 2000、1〜60000ms |
| `rules.fullRevealWaitMs` | 全文表示後の待ち時間 | 10000、1〜60000ms |
| `rules.reconnectGraceMs` | 人数不足で停止した試合の復帰猶予 | 30000、1〜60000ms |
| `rules.showSelections` | 受理した選択文字の共有 | true / false |
| `questionSet.id` / `version` | 使用するDB問題セットの固定版 | mock-hiragana / 1 |
| `owner` / `competitionId` / `rulesetId` | 開催元・大会・ルールの識別子 | 通常は変更不要 |

`owner` は反映先の開催元です。開発参加（`/local-game/`）はインスタンスを持たず、この2ファイル共通のownerと `GAME_CONFIG_PROFILE` の有効版から出題します。2ファイルのownerは同じ値にします。

数値は整数のみ。未定義キー・欠落・型違いを拒否する。人数2〜4などの許容範囲は実装が対応する制約であり、範囲自体の拡張はコード・DB制約の変更と検証が必要です。人数の管理画面は実装済みで、ルール全般・問題セットのCLI設定は維持します。レートは対戦仕様に従います。

runtimeの値も正の整数として読み込み時に検証し、heartbeat間隔が監視期限以上になる設定、再試行間隔が再試行期間以上になる設定、予約期限が待機期限を超える設定、待機期限がセッション期限を超える設定を拒否する。

運用設定は試合ルールと異なり、再起動後の既存接続にも作用する。保存済み期限を延長する操作は行わない。HTTP本文の上限やIDの形式などの入力契約・実装上の制約は設定へ移さない。

<a id="configuration-005"></a>
## DBでの固定と将来の管理画面

反映コマンドはJSONと既存問題のhash・候補を検証し、変更があればルール版・大会版を追加する。同じ内容の版があれば再利用する。

revisionの競合検査とD1のatomic batchで版の割当と `quiz_game_matchmaking_settings` の参照切替をまとめます。過去のルール・大会・問題は更新しない。

新規参加は有効プロファイルをDBから読み、待機列を大会版ごとに分ける。待機中・進行中の試合は保存済み版を維持し、開始直前はその版の問題停止状態などを再検証する。DBに有効設定がなければ参加を拒否し、同梱設定へフォールバックしない。

将来の管理画面ではフォームから同じ構造のJSONを送り、同じ検証・版追加・有効参照切替を使える。管理画面と書込APIは今回未実装。

ブラウザーへDB接続を渡しません。Workerの操作認可と、設置者用CLIの管理者・owner確認を適用します。

<a id="configuration-006"></a>
## 形式の比較と初期導入

JSONは追加パーサー不要で、CLI・API・DBのJSON列で同じデータ構造を使えるため採用した。JSONCはコメントを置けるが読込パーサーが必要で、YAMLも今回の単純な数値・真偽値・参照に対して依存を増やす。

項目の説明はこの文書へ集約する。WranglerのJSONCはツール所定の形式として維持する。[ADR 0008](../history/decisions.md#0008-game-configuration-001)参照。

別環境は[DB管理](database.md)のDrizzle migration・初期seed・プロファイル登録の順で準備する。

ルールの必須項目・型・許容範囲を編集対象JSONから独立させた。標準JSONも読込時に検証し、必須項目の削除や未知キーを拒否する。

<a id="configuration-010"></a>
## ローカルとクラウドの分離

通常開発はローカルD1、認証はClerkのGoogleを使用します。上記CLIはローカルD1用です。クラウドの変更は専用設定と対象DBを確認して行います。詳細は[DB管理](database.md)を参照してください。

## 連携の初期値

相手の接続先URLを管理画面で確認して承認します。公開鍵はURLから取得し、手入力しません。問題の送出と受入は相手インスタンスごとに既定オフです。結果は参加記録に結び付けて所属元へ配送し、共有設定はありません。一括変更は確認した対象・revisionだけへ適用し、後から追加したインスタンスを自動許可しません。「共有問題」では共有元・全カテゴリ／選択カテゴリ・保存先を設定します。カテゴリ別の公開設定は設けません。取り込み専用カテゴリは複数作成でき、通常投稿を禁止します。難易度は簡単・普通・難しいの3区分で共通とし、通常同期で開催先の自動補正や固定値を戻しません。個別除外・解除は「全問題」の操作から行います。

公開情報は毎時Cronで同期し、有効期限は62分です。共有問題は日次Cron（日本時間4時）で同期し、通常の反映時間は最大24時間、有効期限は24時間2分です。急ぐ場合は手動同期できます。取得失敗時は期限内でも新規利用を止め、進行中の固定内容は維持します。[運用手順](operations.md#連携の定期処理と障害復旧)を参照してください。
