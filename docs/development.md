# 作業方針

## 文書の管理

仕様・設計・開発方針はdocsに集約し、AGENTS.mdには入口へのリンクだけを置く。作業前にdocs/README.mdと変更対象の文書を読み、未確定事項はopen-questions.mdで確認する。

ユーザーの回答は未確定事項と該当仕様に反映する。重要な設計変更はADRに理由と影響を残す。実装に伴って仕様・契約・検証結果を同じ変更で更新し、提案や未実施を実績として記載しない。

## 実装の境界

MVPの3段階を順に進める。公開連合、ActivityPub、世界共通レーティング、Docker配布は初期実装に加えない。既存機能と標準・プラットフォーム機能を優先し、必要になる前の抽象化や依存追加を避ける。

フロントエンドへ正解・未表示本文・秘密鍵を持ち込まない。採点と認可はサーバーで実施する。ルール・問題の過去版を書き換えない。DBのmigration、制約、index、権限設定をソース管理する。

変更に応じた検証はverification.mdに従う。文書だけの変更はリンク・整合性を確認し、アプリケーションのテスト済みとは記録しない。

## フロントエンドの実装方針

React + TypeScript + Tailwind CSSを使う。早押しボタン、文字選択パネル、得点表示など、役割のあるUIや繰り返すUIをReactコンポーネントにまとめる。クラス列の長さだけを理由に細かなラッパーを増やさない。

色・文字・余白などの共通値はTailwindのテーマへ集約する。状態による見た目は型付きpropsと完全なクラス文字列の対応表で表現する。クラス名の一部を文字列連結で組み立てず、ビルド時に検出できる形にする。連続的な進捗など実行時の値はCSS変数やstyleで渡す。[テーマ](https://tailwindcss.com/docs/theme)、[クラス検出](https://tailwindcss.com/docs/detecting-classes-in-source-files)参照。

`clsx`と`tailwind-merge`は初期必須依存にせず、次の必要が生じた箇所で追加する。

- `clsx`：条件付きクラスの組み立てが増え、三項演算子や配列の結合より読みやすくなる場合に使う。クラス間の競合解消は行わない。
- `tailwind-merge`（`twMerge`）：共通コンポーネントへ外部から`className`を渡し、既定のTailwindクラスを上書きする必要がある場合に使う。型付きpropsとクラスの対応表で競合を避けられる場合は追加しない。
- `cn()`のような共通ヘルパー：両者の組み合わせを繰り返し使う必要が生じてから設ける。単純なクラス結合のために独自の汎用処理を作らない。

追加時は採用中のTailwind版・カスタムテーマとの互換性を確認し、実際の状態切り替えや上書きが期待どおりに表示されることを確認する。[clsx公式](https://github.com/lukeed/clsx)、[tailwind-merge公式](https://github.com/dcastil/tailwind-merge)参照。

汎用UI基盤やバリアント管理ライブラリは初期導入せず、実際の重複や必要性が生じた時点で検討する。必要な独自CSSは併用してよい。見た目の共通化でもキーボード操作、フォーカス、適切なHTML要素を維持する。

導入は[公式Vite連携](https://tailwindcss.com/docs/installation/using-vite)を基にtailwindcssと@tailwindcss/viteを使用する。採用版は初期実装時に対象ブラウザーとの互換性を確認してlockfileで固定する。現時点では依存追加・ビルド検証は未実施。

## 将来の配置案

最初のアプリ実装で配置を確定する。現時点で空のアプリや共通パッケージは作らない。

- `src/`：UIとWorker/DOを明確に分離した実装。
- `supabase/migrations/`：SQL migration。
- `content/*.md`：インスタンス紹介、遊び方、ルール説明、制作記録。
- `docs/`：仕様・設計・検証結果。

紹介SPAはゲームアプリと独立して扱う。現時点で紹介SPAや付属モックは存在しない。
