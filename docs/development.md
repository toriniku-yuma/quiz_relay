# 作業方針

## 文書の管理

仕様・設計・開発方針はdocsに集約し、AGENTS.mdには入口へのリンクだけを置く。作業前にdocs/README.mdと変更対象の文書を読み、未確定事項はopen-questions.mdで確認する。

ユーザーの回答は未確定事項と該当仕様に反映する。重要な設計変更はADRに理由と影響を残す。実装に伴って仕様・契約・検証結果を同じ変更で更新し、提案や未実施を実績として記載しない。

## 実装の境界

MVPの3段階を順に進める。公開連合、ActivityPub、世界共通レーティング、Docker配布は初期実装に加えない。既存機能と標準・プラットフォーム機能を優先し、必要になる前の抽象化や依存追加を避ける。

フロントエンドへ正解・未表示本文・秘密鍵を持ち込まない。採点と認可はサーバーで実施する。ルール・問題の過去版を書き換えない。DBのmigration、制約、index、権限設定をソース管理する。

変更に応じた検証はverification.mdに従う。文書だけの変更はリンク・整合性を確認し、アプリケーションのテスト済みとは記録しない。

## デプロイの判断基準（2026-09-11）

Workersへのデプロイは、ユーザーから明示的な指示がある場合、または検証にサーバー実環境が必要な場合に限定する。変更のたびに自動でデプロイしない。

デザイン・配色・レイアウト・通常の画面操作は原則 `pnpm dev` で確認する。デザイン見本の更新や、公開URLでも見られるようにすることだけを理由にデプロイしない。

Cloudflare固有の挙動、実環境のbinding・接続・公開originでの認証など、ローカルでは確認できない項目がある場合は、デプロイ前に確認対象とサーバー環境が必要な理由を伝える。この条件を満たす検証では、デプロイのためだけに追加の許可確認を挟まない。既存の無料範囲と、検証APIを有効に保つ指定を維持する。

## フロントエンドの実装方針

React + TypeScript + Tailwind CSSを使う。早押しボタン、文字選択パネル、得点表示など、役割のあるUIや繰り返すUIをReactコンポーネントにまとめる。クラス列の長さだけを理由に細かなラッパーを増やさない。

色・文字・余白などの共通値はTailwindのテーマへ集約する。状態による見た目は型付きpropsと完全なクラス文字列の対応表で表現する。クラス名の一部を文字列連結で組み立てず、ビルド時に検出できる形にする。連続的な進捗など実行時の値はCSS変数やstyleで渡す。[テーマ](https://tailwindcss.com/docs/theme)、[クラス検出](https://tailwindcss.com/docs/detecting-classes-in-source-files)参照。

2026-09-11：共通部品のclassName結合・上書きに、clsx 2.1.1とtailwind-merge 3.6.0を採用した。[clsx公式](https://github.com/lukeed/clsx)、[tailwind-merge公式](https://github.com/dcastil/tailwind-merge)参照。

src/client/lib/cn.tsのcn()で条件付きクラスを結合し、Tailwindの競合を解消する。共通部品では「基本クラス・tone等のバリエーション・外部className」の順で渡し、外部指定を最後にする。固定のクラス文字列だけならcn()で包む必要はない。主操作等の意味は引き続き型付きpropsで指定する。

Tailwind 4.3の採用テーマ・任意値・状態修飾子についてテストする。現在の色トークンにはtailwind-mergeの追加設定は不要。独自ユーティリティ導入時は競合分類の確認を行う。段差のshadow-button・shadow-button-pressedはcn.tsのextendTailwindMergeでshadowテーマに登録する。段差トークンを追加・改名したらこの登録も更新し、通常時・状態修飾子付きの上書きと影の色指定が共存することをテストする。

汎用UI基盤やバリアント管理ライブラリは初期導入せず、実際の重複や必要性が生じた時点で検討する。Tailwindで表現できない場合に限り、必要な独自CSSを併用してよい。見た目の共通化でもキーボード操作、フォーカス、適切なHTML要素を維持する。

導入は[公式Vite連携](https://tailwindcss.com/docs/installation/using-vite)を基にtailwindcssと@tailwindcss/viteを使用する。0Aで依存版をlockfileに固定し、検証画面のビルドとEdgeでの操作を確認した。ゲームUIと他の対象ブラウザーの確認は後続段階で行う。[検証記録](verification-results.md)参照。

### デザインと効果音の実装

見た目は[仕様書のビジュアルデザイン・効果音](specification.md)に従う。素朴なフラットデザインを基本にし、回答ボタンの凸状の段差と押下表現を共通化する。読みやすさと操作状態の識別を維持する。

効果音はイベントと音源の対応を1か所で手動編集できる設定にまとめ、音源の配置・割り当て・差し替え手順を文書化する。音源の選定と実際の割り当てはユーザーが行うため、初期状態は未割り当てとする。未設定や再生失敗を許容し、音声の読み込み・再生完了を入力送信や対戦進行の条件にしない。ブラウザーの音声再生制約に対応し、ミュートと無音時の視覚表示を用意する。

## ソースの配置（2026-09-10更新）

従来はclient/workerの大枠のみを決め、内部の分割計画はなかった。今回、ユーザー要望により以下の責務分割を採用した。将来用の空フォルダーは作らず、機能の着手時に追加する。

| 配置 | 責務 |
| --- | --- |
| src/client/main.tsx | 起動とトップからのリダイレクトのみ |
| src/client/app/ | ルート一覧、ページ選択、起動時のリダイレクト |
| src/client/pages/ | ページ全体の組み立て。API・認証処理を持たない |
| src/client/components/ | Button・TextField・PageHeaderなど複数箇所で使うUI |
| src/client/features/auth/ | Authクライアントの寿命、ログイン・本人確認と認証パネル |
| src/client/features/debug/ | 検証API、操作状態のhook、検証・結果パネル |
| src/client/styles/ | 共通テーマとUIスタイル |
| src/worker/index.ts | HTTPルートの組み立てと共通エラー処理 |
| src/worker/probes/ | 検証APIの認可、検証用DO、DBプローブ |
| src/worker/federation/ | 署名・正規化・送信先検査 |
| src/worker/env.ts | Worker bindingの型 |
| supabase/migrations/ | SQL migration |
| tests/・scripts/ | Workers内のテスト、回帰確認、実HTTP検証 |

今後、1A〜1Bのゲームはclient/features/game/とworker/game/、1Cのマッチングはそれぞれmatchmaking/へ追加する。検証用probes/に正式機能を蓄積しない。各機能が大きくなったら、その機能内でroutes・state・validation等へ責務分割する。client/worker直下に機能ファイルを増やす運用にはしない。

### ファイルと読みやすさ

- 1つのTSXファイルに1つのコンポーネント関数を定義する。main.tsxは起動用の例外でコンポーネントを定義しない。イベントやmapのインラインコールバックは許容する。
- 通信・認証・状態制御はTSファイルやhookへ分離する。1関数制約のために処理を巨大なコンポーネントへ戻さない。
- ボタン・入力欄など繰り返すUIは必ず共通コンポーネントを使う。見た目の種類は型付きpropsで指定する。ページ専用のまとまりはfeatures配下へ置く。
- Biome 2.5.12に統一。pnpm run formatで整形、pnpm run format:checkで整形のみ確認、pnpm run lintで整形・推奨Lint・import整理を確認する。pnpm run checkはLint・型検査・テスト・ビルドを実行する。長い属性・条件・オブジェクトを改行し、処理単位の間は空行で区切る。
- 設計変更後のテストは公開関数を直接importする。TSXの文字列を切り出して実行する回帰チェックは廃止した。

### 画面の配置

トップ / は当面 /debug/ へlocation.replaceで移動する。query/hashも引き継ぎ、PKCE交換前に消さない。認証SDKの初期化はデバッグ画面で行い、交換後に /debug/ へURLを掃除する。AuthのredirectToは登録済みのorigin直下を維持するため、Supabase/Googleの追加設定は不要。

/debug/ は動作検証。配色はstyles/global.cssのTailwind @themeに集約し、採用済みの赤白テーマと段差付きButtonを共通で使う。/design/は削除済み。正式トップを作る時は入口のリダイレクトを外し、デバッグ画面を正式UIへ混ぜない。URL分離は認可の代わりではなく、検証APIのトークン制限を維持する。

紹介SPAはゲームアプリと独立して扱う。見本ページとサンプルクイズは削除済み。ローカルゲームは/game/に配置し、1A・1Bの範囲を実装済み。

### Biomeの対象と設定

biome.jsonで対象をsrc/・tests/・scripts/とルートのTS/JSON/JSONC・index.htmlに限定し、Gitの除外設定も参照する。秘密・生成物・Markdown・YAML・SQLは対象外。Tailwind v4の構文を有効化。HTML整形は実験的対応を明示的に有効化し、現在のindex.htmlで確認した。

推奨Lintはrules.preset=recommendedを明示し、警告もcheckで失敗扱いにする。安全な自動修正はpnpm exec biome check --write .で行う。unsafeの一括適用はせず内容を確認する。エディターのフォーマッターもBiomeを選び、同じファイルにPrettierを重ねて実行しない。tscによる型検査と1 TSX 1コンポーネントの設計確認は継続する。


## スタイルの配置（2026-09-11）

global.cssはTailwindの読込、@themeの色・フォント定義、body・リンク・共通フォーカス等の最低限の全体設定に限定する。リセットはTailwind Preflightを使い、部品・ページ専用セレクターやメディアクエリーを蓄積しない。

各コンポーネントの余白・枠・文字・配色・段差・操作状態・レスポンシブ指定は、そのTSX内のTailwindクラスで記述する。色はbg-keyやbg-accent等で共通テーマを参照し、部品内に色コードを直書きしない。バリアントは同じファイル内の完全なクラス文字列の対応表で管理する。

繰り返す部品はButton・TextField・Panelなどに共通化し、各部品のスタイルをそのファイルで調整できるようにする。単なるクラス列の長さだけを理由に汎用ラッパーやスタイル専用ファイルを増やさない。1 TSX 1コンポーネントを維持する。


### Tailwindの標準値を優先する

余白・幅・文字サイズ・太さ・角丸・ブレークポイントはまず標準クラスから選ぶ。既存CSSの数値をそのまま角括弧の任意値に移さず、近い標準値へ揃える。独自値を全てテーマへ移すことも避ける。任意値は標準で表現できない意図がある場合に限定する。採用済みのボタン段差はshadow-buttonとshadow-button-pressedとしてテーマへ定義する。

### 空行で処理のまとまりを示す（2026-09-11）

Biomeの折り返しだけで可読性を完了とせず、意味のまとまりの境界に空行を1行置く。対象はアプリ、テスト、実行スクリプト、設定ファイル。空行で区切った部分を短い言葉で説明できるかを判断基準にする。

- import群と後続の定義の間、型・定数群・関数・クラスの間に1行。関連する定数や状態宣言はまとめる。
- クラスのフィールド群とメソッドの間、各メソッドの間に1行。
- 関数内は準備、入力確認、主処理、返却などの境界に1行。関連する宣言とその検査は同じまとまりにしてよい。
- ガード節のまとまりと通常処理の間に1行。短いガードを1行ずつ機械的に分離しない。
- Reactではhooks・派生値・イベント処理・returnのまとまりを分ける。
- JSXでは見出し、説明、フォーム、入力群、操作群などの境界に1行。属性ごとや、短いラベル内の要素ごとには増やさない。文章中の空白の意味を変えない。
- テストは準備・実行・検証を分け、複数ケースを扱う場合はケースの境界も区切る。関連するexpect/assertはまとめる。
- 1文ごとの空行や、空行2行以上の連続を避ける。短い関数は無理に分割しない。

Biomeと意味単位の目視レビューを併用する。説明コメントは対象の宣言・処理に隣接させ、間に空行を挟まない。空行を入れるためだけの関数分割・コメント・Lint依存は追加しない。


### ルート定義の責務（2026-09-11）

app/routes.tsはパスと表示コンポーネント、またはリダイレクト先の対応を一覧で宣言する。判定関数、URL操作、認証処理、副作用を記述しない。画面追加時はこの一覧へ追記する。

App.tsxは一覧を参照して表示ページを選び、未登録パスはNotFoundPageへ送る。app/redirect.tsは起動時の転送先を一覧から取得し、query/hashを保ったURLを返す。実際のlocation.replaceはmain.tsxで実行する。認証コールバック判定はfeatures/auth/callback.tsへ置く。

リンクや認証復帰で共用するパスはapp/paths.tsへ定義し、ページをimportしない。これによりルート一覧→ページ→認証処理→ルート一覧という循環依存を避ける。汎用ルーターやルーター依存は追加しない。


### サーバーのルート定義も宣言に限定する（2026-09-11）

ルートと処理を分けるルールはclient/worker双方に適用する。Workerのroutes.tsと入口index.tsはHTTPメソッド・パス・ミドルウェア・ハンドラーの登録とサブルートの組み立てのみを記述し、インライン関数で認可・業務処理・レスポンス生成を実装しない。

probes/routes.tsは対応一覧、probes/authorize.tsは有効判定・トークン認証・Origin確認、probes/handlers.tsは各検証APIのHTTP処理を担当する。共通のhealth・404・エラー応答はhttp/handlers.tsへ置く。既存のDB・DO・署名・送信先検証は各専門ファイルを維持する。

ハンドラーはHonoの型を付けて登録し、ミドルウェアの適用範囲・登録順を一覧で読めるようにする。小さな関連ハンドラーは同じファイルにまとめてよい。1関数1ファイルの制約は設けず、汎用ディスパッチャーは追加しない。


### クライアント・Worker共通のAPIパス（2026-09-11）

HTTP APIのパスはsrc/shared/api-paths.tsのAPI_PATHSに集約する。画面用のapp/paths.tsとは区別し、sharedはReact・Hono・環境変数・秘密情報に依存させない。

API_PATHSは/apiから始まる完全なパスを公開する。クライアントのfetch、Workerのルート登録、CLI検証は同じ定義を参照し、呼び出し側で/apiを追加しない。検証APIの接頭辞はPROBE_PREFIXから構成し、認可ミドルウェアの適用範囲にも使う。検証サブルートは完全パスを持つため入口で/にマウントする。

API追加・変更時は共通定義と登録・呼び出しを同時に更新する。既存URL契約と認可範囲を独立に検査するテストではパスのリテラルを残してよい。共通定義の誤変更によってテストも同時に追従してしまうことを避ける。
