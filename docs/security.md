# セキュリティと運用

## 認証・認可

本人確認は所属Supabase Auth、参加許可と対戦裁定は開催元。外部所属のAuthトークンを開催元のユーザーとして無検証で利用しない。管理者、問題作成者、プレイヤーの操作権限と所有者をHono側で検証する。ログインはメールのマジックリンクとSNSアカウント認証。SNSはMVPではGoogle。管理者初期登録の詳細は実装前に確定する。複数ログイン方式のアカウント連携は所属Authの検証済みsubjectを正とし、受信メールや表示名だけで独自統合しない。

ブラウザーへservice_role、DB接続文字列、インスタンス秘密鍵を配布しない。公開環境変数には公開可能な値だけを置く。Supabaseの公開オブジェクトにはgrantsとRLSを明示する。サーバー側も最小権限ロールを使用し、RLSを迂回できる権限であればAPIの認可を独立して検証する。[公式API保護資料](https://supabase.com/docs/guides/api/securing-your-api)参照。

## 連合の境界

手動承認したHTTPS originとpin済み公開鍵だけを使用する。リダイレクト、内部・loopback・link-local IP、任意URL取得を拒否する。文字列のホスト検査だけでDNS rebinding対策が済んだと扱わない。Workersの送信経路で解決先をどこまで制御・検証できるか先行検証し、必要なら送信先の固定や制限されたegressを採用する。未検証のままSSRF対策済みと記載しない。

kid、有効期間、署名、宛先、用途、本文hash、型、サイズ、nonceとレートを検証する。未知の版や矛盾イベントは隔離し、順位へ反映しない。受信文字列・Markdownを生HTMLとして実行しない。管理画面でも同様にescape・sanitizeする。

鍵更新は管理者の確認を伴う。旧鍵履歴を残し、鍵漏洩時はpeer停止、新鍵の別経路確認、影響時間帯のイベント調査と除外・取消を行う。正常な鍵更新で過去の正当な結果を一括無効化しない。

## ログと制限

トークン、cookie、Authorization、正解、入力解答、問題セット本文、個人メールをログに出さない。例外ログやリクエスト全体の自動記録にも同じ制限を適用する。相関ID、room/match/result/event ID、エラーコードで追跡する。

入力長、WebSocketメッセージサイズ、actor/IP/peer単位のレート、ルーム人数、同時ルーム数、待機ルーム寿命、保存待ち件数の上限を実装前に数値化する。制限超過は明示エラーにし、既存の未保存結果を破棄しない。新規試合を停止する運用を用意する。

## 監視と障害対応

| 観測 | 対応 |
| --- | --- |
| アクティブルーム数、裁定エラー、切断率 | 上限・地域・接続・DO状態を調査 |
| DB保存待ち件数と最古経過時間 | DB接続と制約を確認、同一resultIdで再試行 |
| outbox滞留、最古イベント、最終成功時刻 | peer稼働と承認鍵を確認、配送再開 |
| inbox未投影・隔離件数 | 署名・契約・大会条件を確認、原因修正後に再処理 |
| 同期遅延、投影更新時刻 | 受領と投影を分けて調査 |

UIではローカル保存、peer受領、順位反映を区別する。遅延や隔離を「同期済み」と表示しない。ログ保持期間、個人情報削除、バックアップ頻度、復旧目標RPO/RTO、警告しきい値は公開前の確認項目。

PostgresバックアップだけではDOに残る未保存結果を回復できない。復元対象にDOストレージと鍵履歴・設定を含める方法を先行検証する。復旧後は重複配送と順位再生成を安全に実行する。破壊的な障害試験は分離したデモ環境で行う。

## 0Bで採用した限定送信経路（2026-09-10）

初期検証は手動承認したworker.account.workers.dev形式のHTTPS origin完全一致に限定する。独自ドメイン・別ポート・任意URLは拒否する。Cloudflare管理の名前に限定することでpeer管理者による独自DNSの変更を対象経路から除外し、一般のDNS rebinding対策の実測とは区別する。global_fetch_strictly_publicを有効にし、公開経路、固定path、manual redirectと3xx拒否を使用する。Cloudflareの名前解決・公開ルーティングを信頼境界に含む。

任意の独自ドメインを許可する変更では、内部IP解決・DNS変更・リダイレクトと秘密非転送を実経路で検証するまで有効化しない。単にこのホスト制限を削除して拡張しない。S01全体は未完了。

[公開fetchの公式仕様](https://developers.cloudflare.com/workers/runtime-apis/fetch/)と[Workersのルーティング](https://developers.cloudflare.com/workers/reference/how-workers-works/)を参照。
