## 採用済みの境界

同時参加（2026-09-16承認・未実装）：同じ組織の同じアカウントでは、インスタンスをまたいでも対戦参加・自動マッチング待ちは同時に1つまで。他インスタンスの閲覧・管理操作は可能で、別インスタンスの画面を開いただけで元の試合を離脱させない。部屋ロビー滞在・出題専任・別組織への参加・ゲストとの関係は別途具体化する。

1配置で1組織を運営し、管理画面から複数インスタンスを追加する。ユーザーと管理者は組織共通。モデレーター権限・問題・レート・待機列・部屋はインスタンス別。同組織のユーザーに外部参加許可を要求しない。問題等の共有は個別設定を必要とする。

## 構成案

- 現在のWorker・Supabase Auth・Postgresを組織内で共用する。インスタンス追加でDBやAuthを新設しない。
- 組織とインスタンスは変更しない内部IDを持ち、表示名やURL用の名称から独立させる。具体的なID形式・URLは詳細設計で定める。
- 認証済みのAuth subjectを組織内アカウントへ対応付ける。表示名やメール一致で別アカウントを自動統合しない。
- 初期配置（2026-09-16承認）：最初のインスタンスに既存の問題・設定・結果・レートを引き継ぐ。追加インスタンスではユーザー・管理者を共有するが、問題・戦績・レート・モデレーター権限を自動複製しない。問題の登録・共有設定・権限付与を個別に行う。
- ownerの全列改名は前提にしない。まず既存ownerと移行先インスタンスの対応を定義し、読み書きの境界を明示する。旧原本・固定版・outboxは保持する。
- 本人識別は下記の具体案に従い、既存actorIdを維持する。移行前のGAME_OWNERを組織の変更不可な識別用値として保存し、インスタンスを切り替えてもactorIdを変えない。ハッシュからsubjectを逆算したり、過去の表示名で本人を特定したりしない。未ログインの既存利用者の集計も維持する。
- Workerで本人・対象インスタンス・操作権限を毎回検証する。画面で選択中という理由だけで認可しない。DBの外部キー等でも別インスタンスの問題や設定の誤参照を防ぐ。DBのreader/resultsロールに広い権限がある現状を、利用者ごとの分離が完成している根拠にしない。
- 待機列・予約・部屋・結果保存は同じ開催インスタンスを保持する。異なるインスタンスの部屋IDやトークンを渡した操作も拒否する。既存の保存後ACK・重複排除・終端不変を維持する。

## 第1段階の画面と状態

準備中のテスト対戦（2026-09-16承認・未実装）：組織管理者と対象インスタンスの担当モデレーターだけが参加できるテスト対戦を用意する。一般ユーザーは参加できず、他インスタンスだけのモデレーター権限では参加できない。テストはレートと正式な難易度集計へ反映しない。テストの開始操作・対象問題・人数・履歴の表示と保持等の細部は別途具体化する。

- 初回設定：設置者が組織と最初の管理者を設定する。設置者だけが開始できる仕組みを用意し、誰でも最初のアクセスだけで管理者になれる方式にしない。具体方式は設計時に定める。
- 組織の管理画面：インスタンス一覧と追加、共通アカウント・管理者の確認。インスタンス固有設定には対象名を常に表示する。
- 利用画面：同じログインでインスタンスを選び、そのインスタンスの設定・レート・待機状態を参照する。正式ホームの最終レイアウトは第6段階でも調整する。
- 追加インスタンスの公開（2026-09-16承認・未実装）：作成直後は「準備中」とし、一般ユーザーの一覧に表示せず、参加を受け付けない。管理者と権限を付与されたモデレーターが担当権限の範囲で問題・設定を準備し、管理者が「公開開始」を実行すると一般ユーザーが利用できる。公開後もランク・カジュアルの有効／無効や休止設定に従う。既存環境の移行先を自動的に非公開にする決定ではない。
- 準備中の一覧非表示だけで参加を防いだことにせず、参加APIでも状態と権限を検証する。一般ユーザーが既知のURLやIDを指定しても参加できないことを受入で確認する。
- 公開状態と試合開始可能条件は分ける。ランクの出題候補0件なら新規マッチング受付・試合開始を止め、待機中の人には理由を表示して待機を解除する。運営には登録・承認・停止状態・出題設定等の確認箇所を案内する（2026-09-16承認）。開始済み試合の固定済み候補には遡及しない。共通問題0件だけで全モードの公開を禁止しない。検出・開始・取消の競合を処理する具体契約は詳細設計で定める。
- 候補復旧時（2026-09-16承認・未実装）：利用可能な出題候補が戻れば、候補0件を理由とする受付停止を自動解除する。解除済みの待機者は自分で再参加し、自動で待機列へ戻さない。管理者の手動休止は解除しない。公開状態・モードの有効設定・個別参加制限等も引き続き適用する。
- 第1段階で後続の作問・部屋全機能を実装する必要はない。既存の対戦・履歴と複数インスタンスの境界を成立させ、後続機能でも分離を再検証する。

## 移行手順案（実行しない）

1. 対象環境を指定し、スキーマ版・既存owner・Auth構成・データ件数・結果ハッシュ・利用者別レート・未保存結果・DO状態を調査する。現在のローカルとクラウドの差を確認する。
2. 復元可能なバックアップを準備し、隔離した検証環境で追加型の移行を試す。適用済み0000〜0010の再適用や初期seedの再投入はしない。
3. 組織・インスタンス・アカウントの対応を追加する。既存データを最初のインスタンスへ対応付ける。問題の出典や作問者が現行データで分からない場合は架空の投稿者を補わない。
4. 原本・outboxの件数とハッシュ、固定版参照、本人履歴、インスタンス別レートが移行前後で一致することを確認する。新しいアカウントと過去actorを別人として二重集計しない。
5. 切替時は新規参加を止め、既存試合と未保存結果の処理完了を待つ方式を候補とする。旧DOを新名前空間へ無条件に置き換えない。実際の切替時間・待機列処理は実行計画で確認する。
6. 復帰・認可・結果保存を確認して新規参加を再開する。失敗時は新規書込みを止めて調査し、新構成で受理した結果を捨てる単純なバックアップ巻戻しはしない。復旧手順はリハーサルで検証する。

## 詳細な受入項目案

- 同じアカウントがA・Bへ同時に参加要求しても対戦参加・自動待機は1つだけ成立する。他インスタンスの閲覧・管理や単なる画面切替では現在の参加を解除しない。切断復帰・待機取消・試合終了と組織共通の参加状態が整合することを確認する。インスタンス単位の既存予約だけでは組織内の同時参加防止にならないため、原子的な参加確保・解除と障害復旧の設計を追加する。

- 同一アカウントでA・Bを利用でき、Aのモデレーター権限でBを管理できない。組織管理者は承認済み範囲を管理できる。
- A・Bの問題・設定・待機列・部屋・レートを取り違えない。URLやリクエスト内の対象IDを差し替えても権限外の取得・変更ができない。
- 既存ユーザーのログイン後に過去履歴とレートが途切れず、未ログインの既存ユーザーの結果も保持される。
- 原本・固定版・outboxを保持し、移行後の再試行で結果やレートが二重反映されない。
- 初回設定の重複実行やインスタンス追加の再送で管理者・インスタンスが意図せず重複しない。
- サービス仕様上の質問は少数ずつ確認する。技術的な列名やID形式の選択まで逐一ユーザーの承認待ちにしない。

## 2026-09-16：実装へ落とすための具体設計案

以下は委任された技術設計の整理。仕様の追加承認・実装済みという意味ではない。具体的なDDL・API・DO保存形式は実装着手前に差分設計する。

### 1. 既存の本人識別とデータを保持する

- 組織に変更不可の識別用値を持たせる。既存環境では移行前のGAME_OWNERをそのまま保存し、actorIdの計算を従来と同じ `contentHash({ home: identityNamespace, subject: verifiedSubject })` に保つ。新規構築では新しく割り当てた組織の内部識別値を使う。表示名・URL・利用先インスタンスはこの計算に使わない。
- Auth subjectは必ず既存のサーバー側getUserで検証した値を使う。組織内アカウント表ではsubjectとactorIdをそれぞれ一意に保持し、初回ログインで対応を登録する。過去のactorIdを変更しないため、まだ新構成へログインしていない人の結果やランキングもそのまま残る。
- 最初のインスタンスは既存ownerをデータ参照用の値として引き継ぐ。インスタンスの内部IDとownerは一意対応させ、既存の問題・設定・結果・outboxのownerやpayloadを一括書換えしない。追加インスタンスには既存と衝突しないownerを発行する。
- results/read.tsは引き続き対象ownerとactorIdで取得できる。組織内で同一actorIdを使っても、owner条件を除いてレートを合算しない。アカウント行が未作成という理由で過去result_playersを除外しない。
- 移行前に複数owner・複数Auth基盤・異なる本人識別規則が見つかった場合、この単一旧環境の移行案を機械的に適用しない。対応を調査し、表示名やメール一致による統合を避ける。

### 2. 追加する永続情報と認可

| 情報 | 最低限の役割・制約 |
| --- | --- |
| 組織 | 1配置の組織レコード、内部ID、表示名、変更不可のidentityNamespace、初期設定完了状態 |
| 組織アカウント | 検証済みAuth subject・actorIdの一意対応、組織共通の管理者権限。退会・処分の完成は第3段階 |
| インスタンス | 組織、内部ID、変更不可のデータowner、表示名、準備中／公開。アーカイブ等は第3段階 |
| インスタンス権限 | インスタンスとactorIdの組合せ、付与された既決パーミッション。Aの権限でBを管理できない |

認証→対象インスタンスの存在・組織の確認→公開状態または管理権限の確認→個別操作の認可、の順で処理する。対象はサーバーで解決し、ブラウザーがownerを直接指定して権限判定を省略するAPIにしない。設定・問題の複合参照はownerが一致するDB制約を維持する。

Web管理には必要な表と操作だけを許可したDBロールを設計する。既存の管理用資格情報・migrationロール・service_roleをWorkerやブラウザーへ流用しない。catalog_operatorsはCLI用のDBロール認可であり、Webモデレーターへそのまま渡さない。

### 3. 初回管理者の設定

設置者確認は、初回管理者にするAuth subjectを設置者がサーバー設定へ指定する方式を案とする。subject自体は認証情報ではなく、それを知っているだけでは設定を完了できない。

1. 設置者が初回設定画面から既存のメール／Google認証でログインする。
2. 未設定時のみ、ログイン中の本人の識別子と、サーバー側にその識別子を指定する手順を表示する。
3. 設置者が配置環境の初回管理者設定へ指定する。アプリは指定されたsubjectと、検証済みログインのsubjectが一致するときだけ組織名等の確定を受け付ける。
4. 組織・初期管理者・最初のインスタンスを同一DBトランザクションで登録し、初回設定済み状態を確定する。並行した設定要求は1回だけ成功させる。
5. 完了後は初回設定経路から追加昇格・初期化できない。設定の除去や通常再起動でも初期設定を再開しない。応答消失時は設定済み状態を確認して管理画面へ進む。

設定値をAPIで公開する必要はなく、DB管理パスワード等を初回画面で入力させない。既存データの移行時にも、最初にアクセスした人や過去の参加者を自動的に管理者にしない。移行データと初回設定を結び付ける順序は移行リハーサルに含める。

### 4. 同時参加は既存Matchmakerを組織単位に拡張する

別のロック専用サービスは初期案では追加しない。組織ごとに1つのMatchmakerを使い、既存のactor予約を共通化する。各予約にはinstanceId・mode・roomId・世代を持たせ、相手を探す条件と人数・ルール・問題はインスタンス別に分離する。物理的な調整役の共有は、待機列やレートを混ぜる意味ではない。

- 参加要求時、対象インスタンスの認可と固定条件の取得を経て、保存済みactor予約を確認する。別のインスタンスへの参加中なら新しい予約を作らず、参加先へ戻れる案内を返す。
- 部屋予約RPCの前にactor・instance・mode・room・世代・復帰用情報を保存する。同じ要求の再試行では同じ部屋へ進み、RPC応答消失で別部屋を作らない。
- DB読込中や取消と新規参加の競合には、既存のadmissionId方式を対象インスタンスと結び付けて使う。古い応答で新しい予約を上書きしない。
- 復帰は保存済みの参加先へ戻す。画面切替・切断・一時停止だけで予約を解放しない。ログアウトによるトークン無効化も、進行中試合から自由に次試合へ乗り換える抜け道にしない。
- 待機取消は部屋側の取消成立を確認してから、同じ世代の予約だけを解除する。取消要求の遅延が次の予約を解除しないようにする。
- 部屋の終端状態が永続化されたことを確認したら参加枠を解放できる。結果DB保存の再試行はGameRoomに残し、参加枠解除で未保存結果を削除しない。レート表示は既存の保存確定状態に従う。
- 通信失敗や状態取得タイムアウトは、部屋が終了した証拠にしない。成否不明の予約は同じ世代・部屋で照合し、単なる時間切れで解除して遅延RPCを二重成立させない。
- GameRoomの予約・認証には対象instanceと世代の対応を保持する。旧世代を閉じる場合は遅延した予約を再成立させない確認が必要。具体的な保存形式とRPC契約を実装設計で定める。

現行Matchmakerは予約表の直列処理中にGameRoom RPCを待つため、組織化すると遅い部屋が他インスタンスへ影響しうる。RPC待ちと保存処理の分離、限定した状態照合、世代照合をセットで設計する。組織全体を直列化したまま規模無制限と扱わない。既存の部屋数等の制限も、組織全体へ無言で読み替えない。規模の確認は負荷試験で行い、必要になる前に新たな分散基盤を追加しない。

### 5. API・画面の接続

- 共通認証の後に対象インスタンスを解決する処理を追加し、設定取得・参加・取消・復帰・結果取得・管理操作で共用する。ルート定義に業務処理を埋め込まず既存の責務分割を保つ。
- 対象インスタンスはURL等で明示する。ブラウザー全体の「現在選択中」変数だけで判断せず、複数タブのAでの操作がBへ送られないようにする。
- 部屋トークンは部屋・本人・インスタンスに結び付ける。APIパス変更時はcookieのpath、取消時の削除、既存復帰導線も合わせて設計する。
- 第1段階の画面は、初回設定、組織のインスタンス一覧・追加、インスタンス設定・公開開始、対象が明確な既存対戦と履歴への入口。正式な作問・審査画面は第2段階で追加する。

### 6. 障害・競合を含む検証項目（未実施）

| ケース | 期待する結果 |
| --- | --- |
| 別アカウントが初回設定へアクセス | 設置者指定の本人でなければ管理者登録不可 |
| 初回設定を同時送信／保存後の応答消失 | 1組織・1回の初期設定になり、再送で余計な管理者を作らない |
| 組織名・インスタンス名を変更 | actorId・owner・過去履歴・レートが変わらない |

| 旧データを移行、利用者が再ログイン | 問題・原本・outboxのハッシュ不変、過去履歴とレート一致 |
| 未ログインの旧利用者 | 過去結果・ランキング集計から消えない |
